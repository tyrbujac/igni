**Q1 — Refine.** The pattern is real but the mechanism is undertheorised and partially wrong. "Rendering details fall below prompt resolution" describes a symptom, not a cause. The actual mechanism is a stack: (a) **prompt-resolution truncation** is real but secondary; (b) **cheatsheet anchoring** is doing more work than the note admits — when the spec already supplies `card`, `radius`, theme colors, models satisfice on existing primitives because the cheatsheet has primed a "what counts as styled" frame, and visual chrome below that frame becomes invisible; (c) **training-data bias toward functional code** — frontier models have seen orders of magnitude more "build a todo app" than "match this Figma frame pixel-accurately," so spec-extrapolation under a functional prompt pulls toward logic gaps; (d) the v0.16 panel was explicitly *spec-extrapolation* with no Figma-translation cell, which structurally cannot surface chrome convergence. The honest framing is: cold-test under functional prompts is the wrong instrument for chrome — but that's a property of the *prompt design*, not an immutable property of chrome primitives. Run a Figma-translation cold-test panel and `border:` likely does surface. The note should narrow its claim to "cold-test under functional/spec-extrapolation prompts under-signals chrome" rather than the broader "chrome under-signals in cold-test methodology," because the broader claim immunises the methodology against a fix that's actually available.

**Q2 — Refine, with split judgements.** The blanket extension is too generous. **Border: clean fit** — purely decorative, substitutable by `card`, no semantic load in a functional prompt. **Shadow: clean fit** — same logic, even more so since elevation reads as "card-ness" and `card` already encodes it. **Opacity: counter-example-leaning** — opacity is frequently *functional* (disabled states, loading overlays, modal scrims); a prompt like "build a form with a submit button that disables while loading" should pull opacity invention, and if it doesn't, that's a real signal, not chrome-under-signal. **Rotation / scale transforms: partial fit** — decorative use under-signals, but transforms appear in *interactions* (pressed states, expand/collapse), and an "animated card flip" prompt would surface them; classifying these as chrome obscures that they're mostly animation primitives wearing chrome clothing. **Animation curves: reject the fit** — when prompts say "smooth," "bouncy," "snappy," models absolutely reach for curves; the note's "tentatively" hedge is doing real work and should become a "no." **Advanced radius tokens: clean fit** — pure decoration, fully substitutable. **Gradient: partial fit** — decorative gradients under-signal, but "hero section" or brand-themed prompts pull gradient invention reliably in my experience with similar panels. So the clean-fit set is border/shadow/advanced-radius; the rest are partial or counter-examples, and the note overreaches by listing them as a unified class.

**Q3 — Needs a third leg: peer-language-survey, lightly formalised.** Two prongs aren't enough because Path C as prior is *self-justifying* — Path C was set by the author's reading of Figma vocabulary, and using it as the prior to defend primitives derived from it is circular. Hand-translation as post-hoc validation is good but suffers from N=1-author bias: the same person who wrote the spec is the translation gate. A third leg needs to be **external and pre-flight**. Peer-language-survey is the right choice: if Flutter, SwiftUI, and Compose all surface `border` / `BoxDecoration.border` / `Modifier.border` as first-class and frequently-reached-for primitives in their tutorial canon, that's independent evidence the primitive is load-bearing for designer-engineer fluency, and it's cheap to check. Real-app-corpus-scan is better in principle but expensive and noisy. Designer-interview is too soft. Accessibility-derived list is valuable but narrow (it'd catch focus rings, not decorative borders). Peer-language-survey also has a useful negative: if a primitive is *absent* from Flutter/SwiftUI/Compose first-class vocabulary, that's a flag against shipping it even if Path C says yes. So: **add peer-language-survey as a third leg, framed as "does the designer-engineer's existing toolchain treat this as a primitive or a recipe?"**

**Q4 — Counter-example: color tokens / theme overrides, and almost certainly hover/pressed states.** Color is the cleanest counter-example. Give a frontier model a brand-themed prompt ("build a settings screen for a fitness app, brand color is coral") with no color primitive in the cheatsheet, and it will invent `color:`, `brand:`, `theme:`, or `accent:` syntax in roughly 4/4 cells — color is semantically load-bearing in a way border isn't, because brand identity is part of the *functional* spec, not chrome. This is exactly why theme color overrides shipped in v0.15 with real empirical pull. Hover/pressed states are a second strong probe: any prompt mentioning "interactive" or "button" pulls state-variant syntax invention reliably, because interaction states are behaviorally observable, not decorative. Animation timing under "smooth transition" prompts is a third. The existence of these counter-examples *strengthens* the note's pattern by bounding it: chrome under-signals **when it's decorative and substitutable**; it surfaces normally **when it carries semantic, behavioral, or brand load**. The note should adopt this boundary explicitly, because without it the "visual-chrome under-signals" pattern is too broad to be falsifiable and starts to look like a license to ship any visual primitive on Path C authority alone.

**Q1 — Refine.** The pattern is real in a narrower form, but the stated mechanism is incomplete. “Rendering details fall below prompt resolution” explains part of the zero signal, but not all of it. The stronger diagnosis is: **unprompted app-generation cold tests preferentially expose missing functional/state/data primitives, not visual-spec translation primitives.** Models are rewarded by the task shape for producing something that works, so they invent persistence, drag-and-drop, filtering, date parsing, etc. They do not usually invent border syntax because the task does not make visual fidelity observable. There are also confounders: training data for app code often treats borders/shadows as incidental styling; Igni’s cheatsheet likely frames components and state more strongly than fine-grained styling; prompts like “habit tracker” or “kanban board” do not carry Figma-level visual requirements; and if Igni already has something like `card`, models may use that as a semantic/visual substitute for bordered or elevated containers. So I would not defend this as “visual chrome systematically under-signals because rendering details fall below prompt resolution” full stop. I would defend it as: **general-purpose cold tests under-detect low-semantic visual-fidelity primitives unless the prompt explicitly makes that visual property part of the task.** That is a useful methodology refinement, but the design note currently overclaims.

**Q2 — Refine.** The named primitives do not generalise cleanly as one class. **Advanced radius tokens** are a clean fit: models may say “rounded card,” but they are unlikely to independently invent a structured radius-token system unless the task is explicitly Figma-translation-like. **Gradient** is only a partial fit: ordinary CRUD/app prompts will not surface it, but prompts like “brand landing page with a gradient hero” probably would make models invent `gradient:` or similar. **Opacity** is also partial: it may under-signal as decorative styling, but it becomes semantically salient for disabled states, overlays, modals, scrims, skeletons, and de-emphasis. **Blur** is partial-to-counterexample: “frosted glass,” “blurred background modal,” or “glassmorphism” prompts would likely elicit invented blur syntax. **Rotation** is not clean visual chrome; it can be layout/interaction semantics for carousels, gauges, clock hands, rotated labels, disclosure chevrons, or transform effects, so I would expect cold-test signal under the right prompts. **Scale transforms** likewise are not merely decorative: zoom, pinch, pressed-state scale, hover scale, image crop/fit interactions, and drag affordances can make them surface. **Animation curves** are the weakest fit for the note’s claim: exact easing curves may under-signal, but “smooth transition,” “springy animation,” “bounce,” or “material-like motion” prompts would likely cause models to invent animation timing/easing syntax. So the pattern fits “border/shadow/radius-as-static-Figma-detail” much better than it fits transforms or motion.

**Q3 — Reject sufficiency; add a third leg.** Path C prior plus post-hoc hand-translation validation is not enough as methodology, because it risks becoming “we already decided this belongs, and later we will notice whether we use it.” That may be acceptable as product judgment, but it is not a strong primitive-promotion gate. I would add a **pre-flight visual-translation evidence leg**: sample real Figma files or representative design-system frames, translate them under current Igni, and measure frequency plus workaround cost for the candidate primitive. This could be called a “Figma corpus / hand-translation benchmark,” and it should happen before shipping where possible, not only after. Peer-language survey is a useful cheap sanity check — Flutter, SwiftUI, Compose, CSS, and design systems all make border/shadow concepts prominent, which supports border as load-bearing vocabulary — but it is weaker than corpus evidence because Igni’s promise is Figma-to-source translation, not parity with every peer language. Designer interviews can help name pain, but they are noisy. Accessibility-derived lists are valuable for specific cases such as focus indicators, contrast, disabled opacity, and reduced motion, but they do not justify all visual chrome. For `border:`, the strongest third leg would be: “in representative Figma translations, bordered/stroked containers and inputs occur often, and current Igni forces either omission or non-obvious workarounds.”

**Q4 — Refine; yes, some visual chrome does surface.** A clean counterexample is **colour/theme tokens** under a brand-themed prompt. If the prompt says “build a banking app using a navy-and-gold brand system” or “create a dashboard with primary/secondary brand colours,” models are likely to invent `theme:`, `color: primary`, `brandColor:`, or token-like colour syntax because colour is both visual and semantically named in product prompts. Another likely counterexample is **font weight/size**: prompts mentioning “large hero title,” “bold KPI numbers,” or “small muted captions” would probably elicit invented text-style syntax. **Focus rings** are also a good bounded case: if the prompt says “keyboard-accessible form with visible focus states,” models may invent `focus:` or `focusRing:` even though that is visual chrome, because accessibility makes it semantically load-bearing. **Animation timing** can surface when the prompt says “smooth transition” or “springy pressed state.” These examples show the needed boundary: visual primitives under-signal when they are merely Figma fidelity details, but they can surface in cold tests when the prompt names them as brand, accessibility, hierarchy, interaction, or motion requirements.

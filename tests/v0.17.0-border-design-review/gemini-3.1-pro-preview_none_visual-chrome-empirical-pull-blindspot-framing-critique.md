**Q1 — Refine.** The pattern is real, but the causal mechanism ("rendering details fall below prompt resolution") is incomplete. The deeper mechanism is *functional dependency combined with semantic encapsulation bias*. When an LLM extrapolates syntax for a new language, it prioritizes primitives strictly necessary to satisfy the prompt's state and logic (drag-and-drop, persistence) because without them, the app functionally fails. Visual chrome like `border:` is functionally optional. Furthermore, LLMs possess a strong encapsulation bias derived from high-level training data (like MUI or Bootstrap); if Igni's spec provides semantic tokens like `card`, `button`, or `input`, the LLM assumes those components already encapsulate standard visual chrome (like borders and shadows) by default. Therefore, the lack of cold-test signal isn’t just about prompt resolution—it’s about the LLM assuming the language's existing semantic nouns already handle the visual heavy lifting unless explicitly forced otherwise.

**Q2 — Refine.** The generalization holds perfectly for strictly aesthetic primitives, but breaks down when visual chrome overlaps with functional state. **Gradient** and **blur** are a clean fit: they are purely stylistic, Figma-driven details that LLMs will almost never invent without explicit art-direction in the prompt. **Animation curves** (easing) are also a clean fit: models might extrapolate a generic `animate: true` or `duration: 300ms` to fulfill a "smooth transition" prompt, but they won't unprompted invent specific cubic-bezier curves because the functional goal is met without them. However, **opacity** is a partial fit and potential counter-example: while LLMs won't invent it for aesthetic blending, they *will* frequently extrapolate opacity (or `hidden`/`visible`) to solve functional requirements like "disabled states" or "modal overlays." The pattern only strictly applies to visual primitives that lack a strong functional proxy.

**Q3 — Refine.** The two-prong protocol is insufficient because hand-translation is entirely *post-hoc*; it tells you if the primitive works after you've implemented it, but doesn't justify spending your strict "spec budget" on it in the first place. The methodology needs a third, pre-flight leg: a **Real-app Figma corpus scan** (statistical frequency of the primitive in production designs). If Igni's canonical user is translating Figma, and every new keyword taxes LLM zero-shot learnability, then visual primitives must earn their spec budget through sheer statistical dominance in design files. Borders and shadows will pass this gate trivially (appearing in nearly 100% of files), while niche rendering features (like blend modes or complex SVG filters) will fail. This statistical prior replaces the LLM cold-test as the pre-flight empirical pull, ensuring Igni only ships visual chrome that is actually load-bearing for translation, protecting the language from Figma's long tail of edge cases.

**Q4 — Refine.** Counter-examples absolutely exist, which bounds the "blind spot" pattern strictly to *purely decorative* chrome rather than *semantic* chrome. A primary counter-example is **hover or pressed states**; when prompted to build interactive apps, LLMs routinely invent visual feedback mechanisms (like inventing a `hover:` prefix) because their training data heavily associates interaction logic with visual state changes. Another strong counter-example is **font-weight or basic semantic color** (inventing `color: red` for errors or `weight: bold` for headers); LLMs readily invent these as semantic scaffolding to organize information hierarchy even when aesthetics are not explicitly requested. LLMs will invent visual chrome when it serves as a communication channel for state or hierarchy. They only ignore visual chrome (like borders, shadows, and gradients) when it serves merely as aesthetic decoration.

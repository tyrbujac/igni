**1 — Unified test block + scope-inferred body**
**Hold.** The sequence-of-statements body is the correct shape and perfectly aligns with Igni’s "spec budget" and "no magic" principles. Introducing explicit scopes (like `setup:`, `act:`, `assert:`) would tax the LLM’s zero-shot learnability by adding unnecessary keywords for what is fundamentally just sequential execution. Similarly, tightening the rules to enforce a parse-time order (e.g., rejecting an `expect` followed by another `tap`) restricts valid testing patterns, such as asserting intermediate states during a multi-step user flow. The unified `test "name":` block relies entirely on the developer/LLM ordering operations logically, which is exactly how standard Igni functions execute. 

**2 — Assertion vocabulary**
**Hold.** `expect <bool-expression>` is exactly right, and the alternatives should be firmly rejected. Splitting assertions into `expect <string>` and `assert <bool>` violates the "one way to do everything" principle by forcing the user (and the LLM) to guess which keyword applies to which data type. A matcher API (`expect(x).toBe(y)`) introduces object-oriented dot-chaining, which breaks Igni's visual structure and bloats the spec budget. By restricting assertions to `expect <bool-expression>` and leveraging existing operators (`is`, `is in`, `is empty`), you get massive LLM learnability for free because the boolean evaluation logic is identical to production `if` statements.

**3 — Single-bundle scope**
**Refine (Split scope).** I strongly advise triggering the Falsification Trigger-A path and splitting this into two releases: v0.18 (Core Testing) and v0.19 (Determinism). Bundling the test runner, rendering, event simulation, assertions, deep mocking, textual snapshots, and timer manipulation into a single implementation cycle is a massive risk. Snapshots require new file I/O and diffing infrastructure; mocking `fetch` and `every` requires intercepting Igni’s core reactive event loop. Shipping `test`, `render`, `tap`, and `expect` in v0.18 delivers 80% of the value (solving the first three "walls" in your hard examples) and keeps the implementation strictly within the 3-session budget. Mocking and snapshots are framework-sized features of their own and deserve dedicated Stage 1/Stage 2 critique in v0.19.

**4 — Canonical-example bug check**
**Refine (Critical bugs identified).** There are multiple Pomodonut-style bugs here. First, `snapshot "name"` will silently fail if the UI contains `now()` or randomly generated IDs; without implicit mocking of time/randomness during snapshot runs, textual trees will non-deterministically diff every run. Second, `tap "Sign in"` is highly fragile—if a screen has a "Sign in" button and a "Sign in" header/link, or two identical list items, the selector is ambiguous. There needs to be a disambiguation strategy (e.g., `tap "Sign in" at 1`). Third, `mock every: advance 60s` implies a magic jump. If a UI depends on a `1s` tick to update intermediate state, does `advance 60s` fire the reactive loop 60 times sequentially, or just alter the clock and fire once? Finally, the proposal states that reactive-fetch rules don't apply during tests to make `mock fetch:` synchronous. This violates "no magic" by fundamentally altering Igni's execution model purely for tests.

**5 — Test-scope builtin set**
**Refine (Add list/network inspection, drop `tapped`).** The proposed set is close, but misses critical test vectors. `seen`, `value_of`, and `on` are excellent. However, `tapped("<label>")` should be rejected; tests should assert on the *outcome* of an interaction (state mutation, navigation, fetch), not the interaction itself, which the test literally just invoked via `tap`. What is fundamentally missing is `count_of(<selector>)` to assert list sizes (e.g., "Todo empty" needs to verify 0 items, adding a task needs to verify 1 item). Additionally, `latest_request("<url>")` or similar is mandatory. In a UI-first language, side-effects like form submissions don't always mutate local screen state—they fire off to an API. Without a way to inspect outgoing mock payloads, you cannot test form submissions accurately.

**6 — Cycle-adaptation framing**
**Hold.** Adapting the 9-stage cycle for framework-shaped changes is correct, and shifting Stage 0 prompts to "given screen Y, write tests" is the exact right metric for testing LLM learnability of the new infrastructure. However, I would push back on adding a formal "framework-design" stage requiring a working reference implementation upfront. The point of the Igni cycle is lightweight, iterative spec validation. Requiring a reference implementation *before* Stage 2 locks in implementation details too early and slows momentum. Instead, for upcoming framework-shaped changes (a11y, i18n, animation), rely on the staggered implementation sessions proposed here, but rigidly enforce Stage 0 (LLM prompting) as the ultimate pass/fail gate before a single line of the test runner/engine is coded.

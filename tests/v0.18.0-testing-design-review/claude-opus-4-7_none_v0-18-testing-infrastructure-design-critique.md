# Stage 2 Critique — Design Note 112

**Q1 — Unified test block + sequence body.** **Hold, with one tightening.** The unified `test "name":` is correct and aligns with Igni's "one way" principle — splitting into `test_function`/`test_screen` would be exactly the kind of branch where LLMs guess wrong, and the body content already disambiguates intent (a test calling `format_currency(...)` and asserting on the return is self-evidently a function test; one starting with `render Login` is self-evidently a screen test). However, "no scope concept" should be **tightened, not relaxed**: parse-time error on event-sim before `render` in the same test body. The doc currently says "event-sims require prior render *at runtime*" — that's a runtime check for a statically-decidable property, which violates "no magic." A test file that types `tap "Sign in"` with no prior `render` is always wrong, never conditionally wrong, so the parser should reject it. Resist the explicit-scope-marker temptation; that's the `test_screen:` proliferation reintroduced through the back door. The body is a flat sequence; the only structural rule is "if you simulate events, you must have rendered first," and that rule is statically checkable.

**Q2 — Assertion vocabulary.** **Hold, strongly.** `expect <bool-expression>` + `seen "string"` builtin is the right shape and I'd push back hard on any matcher-API alternative. The chained matcher API (`expect(x).toBe(y).not.toContain(z)`) is the single largest LLM-failure surface in JS testing — Jest, Vitest, and Chai each have ~40+ matchers with overlapping semantics (`toBe` vs `toEqual` vs `toStrictEqual`), and zero-shot generation gets the wrong one routinely. Splitting `expect <string>` and `assert <bool>` is worse: it creates exactly the alias branch the spec budget forbids, and the natural reading of `expect "Please enter a valid email"` is ambiguous (is that a literal-equality check against full output? a substring? a render assertion?). The current design makes the predicate explicit: `expect seen "Please enter a valid email"` reads as English and parses as `expect <bool>` where `seen` is a named builtin returning bool. This composes cleanly with existing operators (`expect result is "£1,234.56"`, `expect items is empty`, `expect "draft" not in errors`) without inventing new ones. The vocabulary is already minimal and the canonical examples demonstrate full coverage.

**Q3 — Single-bundle scope.** **Refine — split snapshot to v0.19, keep mocking in v0.18.** I'd trigger Watch-list-A here. Mocking belongs in the bundle: the offline-state test and the stopwatch test are both core MVP scenarios, and without `mock fetch` and `mock every` you cannot write deterministic tests for any screen with `fetch()` or `every:` — that's most non-trivial Igni screens, so deferring mocking guts the testing story. Snapshot is different: it's a separable feature with its own design surface (golden-file storage layout, diff representation, `--update-snapshots` semantics, what counts as "textual widget tree"), it has the lowest panel signal of the bundled elements, and it's the one element where the canonical-example bug surface is largest (see Q4). The case for bundling snapshot is "tests need regression coverage" — true, but `expect seen` + `expect value_of` + `expect on` cover regression assertions for everything except visual layout, which is precisely where snapshot's design is least settled. Shipping v0.18 as test+render+events+assertions+mocking+sub-second-every and v0.19 as snapshot+animation gives snapshot a proper design cycle alongside animation (which also needs golden-frame comparison). The Trigger-A path is the right read; this panel is the trigger.

**Q4 — Canonical-example bugs.** **Reject the snapshot example as written; flag two real bugs in the others.** The Pomodonut-style hazards: **(1) Duplicate-label `tap`.** `tap "Sign in"` with two buttons labelled "Sign in" (e.g. one in a modal, one behind it) has no defined behaviour in the doc. This needs a spec rule — either "first in render order" (predictable, testable) or "parse-time error if ambiguous at render time" (safer but harder). Recommend: runtime error on ambiguous match, with `tap "Sign in" in <region>` as the future escape hatch when needed. Don't leave it implicit. **(2) `mock every: advance 60s` interaction with multiple `every` blocks.** If a screen has both `every 1s:` (clock tick) and `every 5s:` (poll), `advance 60s` should fire the 1s block 60 times and the 5s block 12 times — but the doc doesn't say, and "advance" could plausibly mean "advance wall-clock by 60s and fire whatever's due" (correct) or "advance the next `every` by 60s" (wrong, ambiguous with multiple blocks). Spec it explicitly. **(3) Snapshot non-determinism.** The `snapshot "dashboard_default"` example is the live bug: any Dashboard rendering `now()`, a random ID, or fetch-derived content produces a different snapshot every run. The doc has no story for freezing `now()` or seeding randomness during tests. This alone justifies splitting snapshot to v0.19 — it needs a `mock now:` or `freeze_time:` companion that isn't in scope. **(4) `mock fetch` + reactive re-fetch.** Q-F's "test-scope override" is correct in spirit but under-specified: if the test mutates a variable that the production code's `fetch()` depends on, does the mock map get re-consulted? It must, or reactive-fetch tests are impossible. Spec: mock map is consulted on every fetch call, including reactive re-fires. Worth stating explicitly.

**Q5 — Test-scope builtin set.** **Refine — add `current_route`, drop `tapped`, defer the rest.** `seen` and `value_of` are non-negotiable; `on <Screen>` is good. `tapped("<label>")` I'd cut: it tests the test harness, not the app — if you tapped the button, you know you tapped it; what you actually want to assert is the *consequence* (`expect seen "..."`, `expect on NextScreen`, `expect value_of(...) is ...`). Keeping `tapped` invites tests that pass without verifying behaviour, which is the worst failure mode for a testing primitive. **Add `current_route`** (or fold into `on`): navigation with parameters (`on Profile, user_id: 42`) needs an inspection path, and `on Profile` alone can't express "we're on Profile *with the right argument*." `count_of(<list>)` is unnecessary — list length is already `list.length` or whatever Igni's existing accessor is, and `expect items.length is 3` reads fine without a new builtin. `errored("<screen>")` is premature; error-state is just rendered content, so `expect seen "Something went wrong"` covers it until a real signal emerges. `latest_request("<url>")` is the most tempting addition (verifying that a screen actually called the API) but it's also the thin end of a deep wedge — request inspection wants headers, body, call count, ordering — and that's a v0.19 design exercise. Ship `seen` + `value_of` + `on` (with route-arg support) + nothing else; let canonical-example friction surface the next builtin.

**Q6 — Cycle adaptation.** **Refine — yes adapt, but add a Stage-1.5 reference-impl gate, not a new top-level stage.** The framing is right: testing is structurally different from a single-primitive cycle, and a11y/animation/i18n will all hit the same shape (multiple syntax elements, mostly implementation work, Stage 0 prompts that test "use the framework" rather than "use the syntax"). The proposed adaptations (bundled Stage 1, Stage 2 critiques bundling, staggered implementation) are correct. What's missing is a falsification gate: a working reference implementation of the *thinnest viable slice* (here: `test "name":` + `expect <bool>` + `render Screen` + `seen`, no mocking, no snapshot) before the full Stage 1 design locks. Call it Stage 1.5 — "build the 20% that proves the syntax compiles and runs end-to-end, then design the remaining 80% with that evidence in hand." This catches the snapshot-determinism bug and the duplicate-label bug *before* they're spec'd, not after. Don't promote it to a full new stage — that's spec-budget for the meta-process — but bake it into the framework-shaped-change adaptation as a required artefact. For animation and i18n specifically, the reference-impl gate matters even more: animation has timing semantics that only surface under real frame budgets, and i18n has loader/fallback behaviour that only surfaces with real locale files. Testing is the easiest of the three; if the cycle can't absorb a reference-impl gate here, it won't survive animation.

1. **Q1 — Hold, with one tightening.** `test "name":` as the only test block shape is right for Igni. Splitting into `test_screen`, `test_function`, `test_component`, etc. would violate the “one way” rule and create exactly the kind of LLM branch Igni is trying to avoid. A sequential body with optional `render` also works: pure function tests should not need UI ceremony, and screen tests become obvious from the presence of `render`, `tap`, `change`, `seen`, etc. I would not add an explicit scope marker. I also would not reject “mixed-shape” tests, because real tests often compute data, render a component, simulate an event, then assert a pure helper result or UI result. The tightening I would make: because the test body is deliberately simple and mostly linear, event-simulation and render-dependent predicates should be a parse-time or preflight error when no prior `render` exists in the same test. `tap`, `change`, `submit`, `snapshot`, `seen`, `value_of`, and `on` should require an active rendered tree. Do not merely fail at runtime if the compiler can know the sequence is invalid.

2. **Q2 — Hold, but define `seen` as a test predicate, not a general lowercase function.** `expect <bool-expression>` is the right assertion vocabulary. It keeps the language small, composes with existing Igni operators, and avoids matcher-chain complexity like `expect(x).toBe(y)`, which is hostile to Igni’s no-bracket/no-alias design. I would reject both matcher APIs and a split between `expect <string>` for content and `assert <bool>` for predicates; two assertion forms create unnecessary choice. The only refinement is terminology/syntax consistency: `seen "string"` should be specified as a test-scope predicate form, like `tap "label"` is a test action form, not as an ordinary lowercase function that violates the “lowercase functions use parens” rule. So `expect seen "No tasks yet"` is fine, but the spec should be explicit that `seen` is special test syntax returning a bool expression.

3. **Q3 — Refine: keep mocking in v0.18, allow snapshot to split if implementation pressure appears.** The core bundle absolutely needs `test`, `render`, event simulation, `expect`, and deterministic mocking. Without fetch mocking, UI tests for normal apps are flaky or impossible; mocking is not luxury scope. Sub-second `every` also belongs here because time-based UI tests and the coming animation work need the same scheduler semantics. Snapshot/golden testing is the shakier part of the bundle. Textual-tree snapshots are much cheaper than pixel goldens, but they still require serialization rules, update workflows, deterministic handling of dynamic values, and CLI flags. I would not trigger a split now, but I would make snapshots the first item to eject under Trigger A or the “>3 sessions” surprise. In short: accept the single design cycle, but treat snapshot as detachable implementation scope. Mocking should not split unless the mock semantics themselves prove underspecified.

4. **Q4 — Refine: there are canonical-example bugs, especially time.** The biggest Pomodonut-style bug is the stopwatch example: `mock every: advance 60s` appears before `render Stopwatch` and before `tap "Start"`. If test bodies are sequential, that advances time before the timer exists or before it has started. If `mock every:` is declarative instead, the example hides that fact and will confuse users. Prefer visible sequencing: `render Stopwatch`, `tap "Start"`, then `advance 60s`, with `advance` as a test statement enabled by mocked time. The scheduler must also specify that advancing 60s fires exactly sixty `every 1s:` ticks after start, not 59 or 61, and that reactive work drains after each tick. `mock fetch:` also needs a quiescence rule: mocked fetch responses should resolve deterministically, reactive re-renders should drain to stability, repeated fetches should either reuse the mapped response or require an explicit sequence, and runaway re-fetch loops need a clear failure cap. Snapshots are not deterministic if rendered content includes `now()`, random values, or live fetch data; either require visible time/data mocks or document that such snapshots will churn. Finally, `tap "Sign in"` must fail on ambiguity. If two tappable elements have the same accessible label, the runner should raise “ambiguous selector” rather than choosing the first.

5. **Q5 — Refine: keep `seen`, `value_of`, and `on`; reconsider `tapped`; add request observation if fetch mocking ships.** `seen` is essential, `value_of` is useful for forms, and `on <Screen>` is a reasonable minimal navigation assertion. I am unconvinced by `tapped("<label>")` as a v0.18 builtin. After `tap "Save"`, asserting `tapped("Save")` mostly proves the test runner did what the previous line asked, not that the app behaved correctly. It encourages implementation-detail tests instead of user-visible assertions. If component callback testing needs this later, it can return with a stronger story. The missing primitive I would seriously consider is fetch/request inspection, because once `mock fetch:` exists, teams will want to assert that submitting a form made the right request. Something like `requested "/api/users"` or `request_count("/api/users") is 1` may be more valuable than `tapped`. I would not add `count_of(<list>)` or general state inspection yet; tests should prefer visible UI and pure-function assertions. I also would not add `errored("<screen>")`; error states should be tested with `seen`. `current_route` may become necessary if Igni has URL/path routing, but for now `on <Screen>` is the simpler canonical form.

6. **Q6 — Hold, with a framework-spike stage.** The cycle adaptation is right: testing is not a 10-line primitive, and the review prompts should shift from “build an app using feature X” to “given this app, write tests that should pass.” Stage 2 should absolutely critique bundling and lifecycle semantics, because the hard parts are runner behavior, determinism, mocking, scheduling, and golden stability, not just parser syntax. I would add a lightweight framework-design spike before final lock: a working reference implementation or executable trace that proves the canonical examples, especially fetch quiescence, time advancement, duplicate selectors, and snapshot determinism. This does not need to be production-quality, but it should be concrete enough to expose false-simple syntax. The same adapted cycle will be useful for a11y runtime, animation, and i18n, all of which are framework-shaped: they involve lifecycle, resource loading, scheduling, fallback behavior, and testability. For these changes, the design note should include not only syntax but also runtime contracts and at least one adversarial example.

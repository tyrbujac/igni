**Question 1 — Composition rules clarity**
The five composition rules are structurally sound, but Rule 4 introduces a subtle semantic ambiguity with the word "proportionally." In the context of flexbox or Flutter, "proportionally" implies the existence of variable flex weights (e.g., flex-grow ratios of 2:1). However, the artifacts strongly imply Igni’s `fill: true` is a boolean toggle—siblings simply split available space equally. If there are no variable weights in Igni, stating that the remaining space is redistributed "proportionally" is misleading and might cause an LLM to hallucinate a non-existent flex-weight syntax. To fix this, change the phrasing to state that remaining space is redistributed "equally among remaining uncapped siblings." Otherwise, the freeze-and-redistribute algorithm is explained perfectly and intuitively, even for a reader unfamiliar with Flutter's underlying layout engine.

**Question 2 — Box-model rule (rule 5)**
This is arguably the strongest section of the provided spec. The explanation is exceptionally clear, and you should not change it. By providing the exact arithmetic (480px outer, 24px padding on each side, leaving 432px inner) you completely eliminate the "max width vs. content width" confusion that plagues many custom UI frameworks. Furthermore, explicitly referencing CSS `box-sizing: border-box` is a brilliant cognitive hook. LLMs and human developers alike are already deeply trained on CSS box model concepts; naming the exact CSS equivalent anchors the Igni specific behavior to a universally understood standard, virtually guaranteeing accurate mental mapping and code generation. 

**Question 3 — Cheatsheet density**
The cheatsheet currently leans too heavily on dense text for its composition logic. While brevity is the goal of a cheatsheet, layout composition is inherently spatial and visual. The text "uncapped fill: true siblings absorb redistributed slack" is accurate but dry. You should absolutely include a second, brief example demonstrating the `fill: true` and `max_width` interaction. In a UI-first language, developers (and LLMs generating layouts) will frequently need to build responsive rows or columns where one element is rigid and another stretches. Paying the density cost of three or four extra lines of example text will drastically reduce errors, as users tend to copy-paste cheatsheet examples as their starting templates rather than translating prose rules into syntax. 

**Question 4 — Micro and the absent full token**
The explicit "no full token" clause is a great start, but it does not go quite far enough to protect against LLM hallucinations. An LLM primed by CSS and Tailwind will likely see "no full token" and immediately pivot to guessing `none`, `auto`, or `max`. The spec itself mentions avoiding both `none` and `full`, but the micro document only bans `full`. Because Igni explicitly treats aliases as failure branches, you need to plug the remaining obvious CSS translations. Changing the micro text to explicitly forbid the "holy trinity" of web defaults—for example, by writing "omit for uncapped (no full/none/auto tokens)"—will provide a much stronger negative constraint to keep an LLM on the canonical path. 

**Question 5 — Anything else**
There is a minor but important inconsistency regarding axis alignment in the composition rules. In Rule 2, the text states that when a layout hits its cap, the unused space is handled and final placement follows the parent's `align:` property. This makes perfect sense for a capped layout inside a vertical parent, where `align:` controls the cross-axis (horizontal placement). However, if the parent is a horizontal layout, capping a child's width limits its main-axis dimension. On the main axis, extra space is typically governed by `spread:` (which controls distribution along the primary axis), not just `align:`. Rule 4 correctly notes that slack belongs to the parent and is governed by parent `align:` / `spread:`, but Rule 2 only mentions `align:`. Updating Rule 2 to acknowledge that main-axis slack in a horizontal parent relies on `spread:` will close this logic gap and prevent developers from mistakenly trying to use `align:` to control horizontal spacing within a row.

- **Igni is a small, declarative UI language** for building screens, components, layout, state, and simple interactions with a strict, indentation-based syntax. It is syntax-only, uses built-in primitives for UI, supports reactive state, navigation, shared state, async fetches, and light logic, but keeps everything inside a narrow app-UI model rather than being a general-purpose programming language.

- **It is best suited for simple to moderately interactive app-style interfaces** such as mobile or dashboard screens, CRUD flows, forms, profiles, settings pages, lists, detail views, small productivity tools, and lightweight data-driven apps. It fits apps made from screens, buttons, inputs, conditional rendering, async loading states, and reusable components more than graphics-heavy, algorithm-heavy, or highly custom systems.

- **It optimizes for clarity, speed, and consistency of authoring**: one obvious way to express UI, minimal syntax, built-in primitives instead of large libraries, direct state binding, simple event handling, and automatic reactive re-evaluation on reassignment. The design favors readable structure, fast prototyping, and reduced boilerplate over flexibility or deep abstraction.

- **It differs from framework-heavy UI code by removing most moving parts**: no large API surface, no multiple patterns for state/rendering, no custom truthiness rules, no complex component lifecycle model, no mutable in-place list updates, and very limited function/component behavior. Instead of assembling many concepts from a framework, you describe screens and components directly with a constrained set of built-ins.

- **The main constraints to remember are the language’s strict limits**: indentation and colons define blocks; primitives only appear in screen/component bodies; screen/component args are immutable; list items cannot be mutated in place and must be reassigned; no cross-screen function calls; `on change:` requires `bind:`; `emit` only works inside event handlers; there is no truthiness; conditionals use explicit boolean checks; max nesting depth is 4 for `layout`/`screen`/`component`; and the language intentionally avoids aliases or multiple ways to solve the same problem.

1. **Hold.** The bundling argument still carries. Shipping animation without any snapshot surface would create primitives that are hard to regression-test, and waiting for image-fidelity snapshots before shipping any snapshot support would overfit v0.19 to the hardest version of the problem. The better v1.0 path is: ship animation + deterministic text/render-tree snapshots now, then design image/golden snapshots later with real pressure. The one refinement I would require is that “text-tree snapshot” must not mean “only visible strings”; it needs to serialize enough render-tree structure to make animation regressions observable: node identity, branch/list structure, component names, relevant layout/chrome tokens, and transition/spring state where applicable. If the snapshot only records `["Loading…"]` or `["Tyr"]`, it does not verify that `transition: fade` existed. But that is a snapshot serializer refinement, not a reason to split the releases. Animation-without-snapshot first would produce more untested semantics; snapshot-with-image-fidelity later would delay useful deterministic regression testing behind font/rendering/platform complexity.

2. **Hold.** `spring(value)` survives the Flutter-runtime pressure-test. For the SearchBox case, the Igni shape is straightforward: `items = []`, `row_height = 44`, `dropdown_height = spring(items.length * row_height)`, then render the dropdown with `height: dropdown_height`. The hypothetical duration shape would be something like `if items.length > 0: layout height: items.length * row_height, transition: 200ms:` or `layout height: items.length * row_height, transition: 200ms:`, and that is easier for an LLM to misuse because it blurs three meanings: conditional replacement, scalar interpolation, and timing control. `spring(target)` composes better with lexical reactivity: reassignment changes the target, the binding remains the animated value, and no user-visible controller lifecycle leaks into the source. Flutter being duration/controller-oriented is an implementation inconvenience, not a language-design blocker: Igni can codegen a keyed implicit animation/controller behind the lexical `spring` binding, map it in devtools to that source binding, and centralize reduced-motion behavior by making `spring(value)` return `value` immediately when motion is disabled. The main caveat is that true spring physics in Flutter may require generated controller state rather than a trivial `TweenAnimationBuilder`, but the cause remains explicit in source. Flipping to duration would add parameter surface, invite per-call timing bikeshedding, and fight “one way to do everything.”

3. **Refine.** The Q1/Q5 boundary is basically clean, but it needs a hard diagnostic rule to prevent workaround culture. The rule should be: `transition:` is only valid on a container whose immediate dynamic child set changes through `if`/`else` or `each` insertion/removal/replacement; it is not a scalar/layout/style animation mechanism. If an LLM writes `label count, transition: fade` expecting the number to animate, or puts `transition: slide` on a layout whose only changing field is `height`, the compiler should reject or produce a targeted error: “Use `spring(value)` for changing values; `transition:` only animates child replacement.” That small patch keeps one way to do everything: branch/list presence changes use `transition: fade|slide`; numeric/layout values use `spring(value)`. Token-only also survives. Adding `transition: 200ms` would create a second path for animation and immediately reopen duration/curve/API-budget questions.

4. **Refine.** There are several Pomodonut-style edge cases, but none require flipping the primitives. First, `spring()` inside `each` must have stable identity: the spring state should be keyed by the lexical binding plus the row identity, not by transient list index, or progress bars will reset/jump on reorder/filter. If Igni does not already require stable row identity, v0.19 needs either an `each` identity rule or a clear compiler requirement for animating per-row state. Second, `freeze_time:` must freeze `now()`/civil time only; it must not suppress `mock every: advance`, timers, or animation scheduler advancement, or animation tests become impossible. Third, `snapshot` should capture the current rendered frame at the current test scheduler time, not the spring target. Users who want the final state must `advance` enough time first. The example `expect value_of(displayed_steps) is 100` after exactly `1000ms` is risky unless `spring()` has a specified snap-to-target threshold/deadline; otherwise canonical tests should use a larger settle advance or the runtime must define deterministic settling. Fourth, `transition: fade` across `loading → loaded → error` is fine only if branch identities are stable and distinct, so the generated Flutter `AnimatedSwitcher` keys must represent the branch/item identity, not merely child type or text.

5. **Hold.** Text/render-tree snapshots are the right v0.19 scope. They will miss real bugs: color regressions, spacing/padding drift if not serialized, overflow/clipping, z-order, font rendering, icon/raster changes, opacity/slide interpolation fidelity, responsive pixel breakpoints, and platform anti-aliasing differences. But image/golden snapshots are a substantially harder primitive: device size, DPR, fonts, themes, rendering backend, CI determinism, baseline update workflow, and accessibility/reduced-motion interactions all matter. If v0.19 tries to solve that now, it risks delaying both snapshot and animation behind the most brittle testing mode. A few advanced users may hand-write Flutter image golden tests, but that is acceptable evidence for a focused v0.20+ design rather than proof that v0.19 is wrong. The key is to make v0.19 snapshots useful enough: serialize semantic tree structure plus relevant layout/chrome/animation attributes, not just strings.

6. **Refine.** Do not add richer time vocabulary in v0.19, but specify the existing forms more tightly. `mock now:` and `freeze_time:` should control civil time returned by `now()`. Existing `mock every: advance` should control the test scheduler/animation clock and should continue to fire timers/every-blocks even when civil time is frozen. Repeated `advance 16ms` is enough for step-through-frame testing; `advance 1000ms` is enough for settle-style tests. `replay`, `step`, `at`, and `tz` are tempting, but each opens a separate design surface: replay is visual-debug tooling, step is syntactic sugar over `advance`, `at` overlaps `mock now:`, and `tz` belongs with i18n. The one required patch is scoping clarity: `mock now:` should be ambient for the test or mock block according to existing mock rules, while `freeze_time:` should have an unambiguous block extent. No aliases, no second way to freeze time.

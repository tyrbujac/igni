# Stage 2 Panel Review — Doc 113

**Q1 — Bundling rationale carry-forward: HOLD.** The bundle survives a fresh look from this side. The strongest argument isn't either of the symmetric ones in the doc ("animation needs snapshot to be verifiable" / "snapshot needs animation as highest-error-surface") — it's the third one: both need `mock now:` / `freeze_time:`, and designing that surface twice is the actual cost of splitting. The alternative — animation-only v0.19, snapshot+image-golden v0.20 — sounds tidier but creates a six-month window where every animation example in the docs is *claim-only* (no test surface), which is exactly the failure mode doc 112 was built to prevent. It also forces v0.20 to relitigate text-tree-vs-image scope under pressure to ship *something* testable for animations, which is a worse design environment than v0.19's current "text-tree first, image deferred to focused iteration" framing. The only real cost of the bundle is implementation-session count (Trigger B exists for that), and the split-on-overrun escape valve is already specified. Hold the bundle.

**Q2 — Spring vs duration: HOLD, with a caveat.** The Flutter outlier is real but not load-bearing for the lock. Sketching the SearchBox: (a) `dropdown_height = spring(items.length * row_height)` is one line, reads as "this value tracks that value smoothly," and the lexical-reactivity story is exactly the existing one — `items` reassigns, screen re-evaluates, `spring()` interpolates from previous frame to new target. (b) `transition: 200ms` on a height value has no anchor in the language: transition *between what and what*? It needs a controller, a from-value, an AnimationController lifecycle — all the Flutter machinery the language was supposed to hide. Variant (b) is dramatically easier for an LLM to misuse because there's no syntactic forcing function for "where does the from-value come from"; LLMs will invent `previous_value` variables, `useEffect`-style hooks, all the bracket-hell patterns Igni exists to delete. The Flutter-runtime concerns (reduced-motion, AnimationController lifecycle, devtool integration) are codegen problems, not surface-syntax problems — `spring(value)` lowers to `TweenAnimationBuilder` with a spring curve and a system-default duration, and reduced-motion is handled at codegen by collapsing duration to zero. **Caveat (refine-adjacent):** the spec should explicitly note that `spring()` reads the OS reduced-motion setting at codegen, because if it doesn't, accessibility (already a v1.0 blocker at 4/7) gets worse. That's a one-sentence addition, not a lock change.

**Q3 — Animation-surface boundary: REFINE.** The boundary itself is clean conceptually — `transition:` is for tree-shape changes, `spring()` is for value changes — but the doc underspecifies the leak case the question names. An LLM faced with "animate this number changing color from red to green" has two routes: `color = spring(target_color)` (does spring work on colors? the spec doesn't say) or `if value > threshold: label X, color: green else: label X, color: red` with `transition: fade` (forcing a conditional-render swap to get the animation primitive that's more obviously documented). Both are bad: the first is undefined behavior, the second is the workaround the question warns about. **Smallest patch:** the spec for `spring(value)` must explicitly enumerate which value types it interpolates — at minimum numbers, lengths, and colors — and the error message for `spring(non_interpolatable)` must say *"use `transition: fade` on a conditional render instead."* That single error message closes the leak without adding surface. Without this, every cold-test prompt involving "animate a color/opacity/size" is a coin-flip on which primitive the LLM reaches for, which is exactly the LLM-accuracy regression the language is designed against.

**Q4 — Canonical-example bug check.** Three of the four sub-questions surface real bugs. **(a) `spring()` in `each`:** the StepCounter example works because `displayed_steps` is screen-scoped, but a per-row `progress = spring(item.progress)` inside `each item in items:` requires the spring to maintain per-row interpolation state keyed by row identity. If list reordering happens, does the spring state follow the item or the position? The doc doesn't say. This is a Pomodonut-class bug: the syntax looks right, runs fine on a static list, and silently animates wrong values when the list reorders. **Spec must specify spring-state keying** — almost certainly by stable row key, matching how Flutter's `Key` system works. **(b) `freeze_time:` + `mock every: advance`:** genuinely ambiguous in the current doc. If `freeze_time:` freezes `now()` but `advance 1000ms` fires every-blocks, then `every 100ms:` inside a frozen-time block fires 10 times while `now()` returns the frozen value — which is probably what animation testing wants but is *deeply* confusing for relative-time UI testing. The semantics need to be stated, not inferred. My recommendation: `freeze_time:` freezes `now()` only; `advance` advances both wall-clock-for-every-blocks *and* the frozen `now()` value by the advance amount. That gives one consistent mental model. **(c) snapshot of a `spring()`'d value:** must capture the target, not an intermediate frame, otherwise snapshots are non-deterministic by construction — and the doc should state this explicitly because users will expect "what's on screen right now," which during animation is the intermediate. The fix is conceptual: snapshots are logical-state, not visual-frame; image-golden in v0.20 is where intermediate-frame capture lives. **(d) third-state assignment during `transition: fade`:** Flutter's `AnimatedSwitcher` handles this (interrupts the in-flight transition and starts a new one), so the codegen target is fine, but the spec should state the interrupt semantics. **Refine** all four into the spec; (a) and (b) are blocking, (c) and (d) are clarifying.

**Q5 — Snapshot scope: HOLD.** Text-tree-only is the right v0.19 scope. The regressions text-tree misses are all visual: layout overflow, z-order/stacking bugs, rendered-but-clipped content, color contrast, font fallback, RTL mirroring. None of these are catchable by image-golden either *without* a separate design pass on tolerance, platform-pixel-density normalization, and CI-environment determinism — image-golden done badly is the single largest source of test flakiness in real Flutter codebases, and shipping it under v0.19 time pressure produces exactly that. The deferral does leave a gap (Igni users will hit a layout-overflow bug that text-tree snapshots passed through), but the workaround isn't "hand-write image comparison" — it's "use Flutter's existing `flutter test --golden` on the generated output," which is a fine v0.19 escape hatch and provides empirical signal for v0.20's design. The compounding-signal-pattern principle applies: ship the cheap thing, watch what users reach for, design the expensive thing in isolation. Hold.

**Q6 — Time-mock bundling: HOLD.** `mock now:` + `freeze_time:` + `mock every: advance` is sufficient surface for v0.19's use cases and probably for v0.20's. The richer-vocabulary candidates the question lists are all real but premature: `replay` (time-windowed frame replay) is image-golden territory and rides with v0.20's image-snapshot work; `step` (step-through-frames) is a visual-debugger feature, not a test-vocabulary one, and belongs in tooling not language; `at` is just sugar over `freeze_time:` and adds an alias (rejected on principle); `tz` is i18n's problem and must be designed with the i18n primitives in v0.21+, not pre-empted now. Adding any of them now violates spec budget. The one risk is that `freeze_time: <iso-with-tz>` doesn't disambiguate "freeze the wall clock" from "also freeze the system timezone," which matters the moment i18n lands — but the patch there is to *not* couple them in v0.19 (`freeze_time:` freezes the instant only, not the zone) and let i18n design `mock tz:` separately when its design surface is open. Hold the v0.19 surface; reject the vocabulary expansion; flag the timezone-coupling decision to v0.21's design note.

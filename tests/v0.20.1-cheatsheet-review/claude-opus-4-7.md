**Q1 — What's strongest.** The reactivity section is the standout. The "starts at, not resets to" framing for top-level assignments answers the obvious confusion *before* it bites, and the `total = count * price` versus `total()` callout puts the React/Vue/Svelte importer's #1 footgun in the exact place they'll meet it. The transitive-reach rule plus the "no-op for the UI by design" corollary is doing rare and genuine work — it pre-empts the question every reactive-framework reader has on first encounter and answers it without hand-waving. The Todo tour at the top is also load-bearing: 17 lines, every line annotated, every primitive that matters touched. It's the right shape for a cheatsheet entry point. Smaller wins: the `transition:` versus `spring()` boundary explicitly states "they never overlap" and surfaces the compiler error that points readers to the right primitive — that's good design and good docs reinforcing each other. The case-asymmetry callout for `contains()` versus `is`, the `round()`-returns-a-string warning, and the reduced-motion behaviour of `spring()` are exactly the right level of "you would not figure this out unless someone told you, so we are telling you." The PascalCase/lowercase-call-style enforcement is a small choice that pays off across every example.

**Q2 — What's weakest.** The theme section. The "two `text:` surfaces" callout admits a design wart — `theme: text:` and `theme: color: text:` collide on the keyword and the parser disambiguates by position. The cheatsheet handles it gracefully but the underlying ambiguity leaks through, and the paragraph spent disambiguating is a tax every reader pays. Either rename one or accept that this section will always be the thorniest. Adjacent: the structural-sub-block introduction is dense — `scaffold:` / `appbar:` / `text:` arrive together with little build-up and the only example mixes user-defined tokens, built-in token overrides, and structural overrides in one block. Splitting "override built-in colours" from "structural chrome defaults" into two smaller examples would let each idea land. The borders "Selected-state pattern" subsection veers prescriptive ("one screen-internal function per axis") in a way that reads as a how-to-write-Igni recipe rather than reference material; it belongs in a patterns guide. The `input bind: shared.X` exception is genuinely important and the workaround is non-obvious, but it's buried mid-section in a blockquote — it deserves more visual weight, possibly its own subsection. Finally, the strings-builtins surface (`contains`, `upper`, `lower`) plus the "no `capitalize` or `title_case`" disclaimer is too austere without a "store strings naturally, format at render" example to motivate the absence.

**Q3 — Genuine semantic uncertainty.** Several places I read carefully and still don't know the answer. First, lambdas — "single-expression, one parameter, used only as arguments to list builtins" — can the body call a screen-internal function? `filter(items, item => is_valid(item))` looks like it should work but every example uses pure expressions, so I'd be guessing. Second, the `theme dark:` auto-fall-back rule clearly applies to colour tokens, but what about structural sub-blocks? If light declares `scaffold: background: surface` and dark only overrides `surface`, does dark's scaffold redirect through dark's `surface` automatically, or does the scaffold sub-block need redeclaring? The example redeclares both and the prose doesn't pin this down. Third, `spring()` inside `each` keys on "row identity" but the term is never defined — is it object reference, structural equality, or a key argument I missed? For a list of primitives there's no identity surface at all. The same question applies to `transition: fade` on `each` insert/remove. Fourth, `locate()` is described as "one-shot" but its lifecycle on screen revisit isn't spelled out the way `every`'s is. Fifth, persistence — `fetch()` is the network story; nothing in the cheatsheet describes local storage, and a notes/settings app needs that immediately. Sixth, `seen "string"` matches within a single primitive's text, but `label "Welcome, " + user.name` evaluates the concatenation before render — is the rendered text one primitive or two? Seventh, what happens when a `fetch()` inside an `every` block errors mid-poll — does the next tick fire normally and clear the error, or does the error state persist until manual reset?

**Q4 — Cross-language-prior check on v0.20.** Theme variant pairs map cleanly onto Compose's Material `lightColors`/`darkColors` model and SwiftUI's `ColorScheme` environment, less cleanly onto CSS's `@media (prefers-color-scheme: dark)`. A Compose user will guess the pattern correctly; a CSS-only reader will hunt for the media-query equivalent and find it under `shared.theme_mode`, which is fine but would land easier if the docs said "this is the SwiftUI/Compose declarative pair, not the CSS conditional." The auto-fall-back rule diverges from every prior — Compose, Tailwind, and CSS all require explicit redeclaration in the dark variant. Igni's choice saves real boilerplate (brand stays brand) but a Tailwind reader will write the dark block thinking they're being thorough and end up surprised when their omissions are inherited; the cheatsheet does state the rule but it's worth a stronger flag because the prior is so consistent across other ecosystems. Structural sub-blocks (`scaffold:` / `appbar:` / `text:`) map onto Material's nested `MaterialTheme(colors=, typography=, shapes=)` shape and Tailwind's `theme:` config branches — readers from those backgrounds will find the pattern familiar. The `text:` keyword collision is the one place priors actively mislead: every other framework keeps colour and typography in separate top-level branches, so a Tailwind/Material reader will not expect to see `text` in two positions and will trip on first read. `shared.theme_mode` with `"system" | "light" | "dark"` aligns cleanly with SwiftUI's `preferredColorScheme(_:)` and Compose conventions; "system" as default is the right default and the prior holds. The `spacing/N` numeric scale is the cleanest alignment in v0.20: Tailwind users reach for `spacing/3` and get 12px exactly as expected, Material users reach for `medium` and get the semantic shorthand. The "multiply N by 4" rule happens to match Tailwind's effective behaviour. The "numeric `gap: 12` is not valid" rule is the right discipline but will surprise CSS readers who expect raw pixel values to be accepted everywhere.

**Q5 — Fit and limits.** Project (a), the canvas + source editor + state inspector + AI-agent tool: mostly wrong tool. The chrome around those panels (toolbars, dropdowns, layout splits, modal dialogs) maps fine to Igni. Everything inside the panels hits walls: no canvas primitive (no paths, no drawing, no SVG embed), no code editor (no monospace primitive with cursor management, no syntax highlighting, no virtualised line rendering for large files), no streaming primitive for AI responses (`fetch()` is described as request/response with no token-stream story), and no keyboard-shortcut layer at the language level. You'd build the chrome in Igni and host the actual editing surfaces in something else, which probably means writing the whole thing in Flutter directly to avoid the boundary. Project (b), the notes app with list/editor/settings: Igni's sweet spot. The Todo example *is* this app at smaller scale. Screens, `navigate to`, `shared:` for the notes list, `each` for the list view, `input bind:` for editing, `shared.theme_mode` and `toggle bind: shared.X` for settings — all map cleanly. Two real frictions: persistence isn't described anywhere in the cheatsheet (notes need to survive app restart, and `fetch()` is a network story not a local one), and `input` is implicitly single-line — no `multiline:` modifier shown, so a notes app whose notes are more than one line is already off the documented surface. If those two are solved features that just aren't in this cheatsheet, fine; if they're genuine gaps, this is the project where they'd surface first. Project (c), the data-entry/dashboard tool: form chrome maps cleanly — `input`, `dropdown`, `checkbox`, `toggle`, `slider`, all with `bind:` and `on change:` for validation; `if`/`else` rendering for error messages; `each` over a results list. The walls hit fast on the dashboard side: no chart primitive of any kind (bar, line, scatter, pie — none), no table primitive with sortable/resizable columns (each + layout horizontal works for simple grids and runs out around column resize and virtualisation), no date type, no date picker, no file upload, no pagination primitive. For a CRUD form-and-list internal tool with simple presentation, Igni fits well. The moment a stakeholder asks for a chart, you're either embedding Flutter directly or shipping screenshots.

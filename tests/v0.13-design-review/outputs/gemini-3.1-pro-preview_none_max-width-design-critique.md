Here is a review of the v0.13 design note, answering the five questions raised.

**Question 1 — Token naming**
The choice of "phone", "tablet", and "desktop" leans heavily into Material Design’s breakpoint nomenclature, which is a strong pragmatic choice for LLM zero-shot accuracy. Models trained on the vast corpus of web development tutorials and UI frameworks will inherently understand that "phone" means roughly 400 to 500 pixels, "tablet" means roughly 700 to 800 pixels, and "desktop" means 1000+ pixels. This intuitive mapping limits hallucination. 

However, the naming absolutely overcommits to the device metaphor, which will cause semantic friction. When building a macOS application in Igni, a developer (or an LLM generating code from a prompt) might need to constrain a left navigation sidebar or a settings panel to 480 pixels. Applying a "phone" token to a desktop sidebar is semantically jarring. If a prompt explicitly asks for "a narrow desktop sidebar", an LLM might actively avoid the "phone" token because the semantic context clashes, potentially hallucinating a non-existent token like "sidebar" or "narrow". Semantic-purpose names (such as "compact", "medium", "wide") or Tailwind-style sizes (small, medium, large, extra-large) avoid this metaphor trap. That said, because Igni already uses "small", "medium", and "large" for spacing and radii, reusing them for container widths would overload the terms and confuse the LLM regarding expected scale. Therefore, while "phone / tablet / desktop" brings device-metaphor baggage, it remains the safest choice to clearly distinguish layout-width tokens from spacing tokens in the model’s latent space.

**Question 2 — Pixel ladder**
The proposed ladder of 480, 768, and 1200 hits most standard UI breakpoints, but it completely misses the narrower constraints required by typical desktop UI patterns. Walk through the common patterns: a 768-pixel tablet constraint is mathematically perfect for an optimal article body width (roughly sixty-five to seventy-five characters per line). A 1200-pixel desktop constraint perfectly handles dashboard columns and marketing hero sections. A 480-pixel phone constraint works well for standalone centered cards (like the MiCard example) or large authentication modals.

Where the ladder fails is on standard sidebars, navigation drawers, and constrained input clusters. A 480-pixel sidebar is comically wide on most screens. The design note itself inadvertently highlights this gap by mentioning that Igni currently relies on a hardcoded 320-pixel constraint for inputs. If 320 pixels is the internal standard for inputs, it should be exposed as a token. Expanding the ladder to five tokens by inserting a 320-pixel token (perhaps named "compact" or "drawer") below "phone" would perfectly resolve this. Five tokens still fits cleanly within the project's rule of thumb, it covers the sidebar/input use-case that 480 pixels is too wide for, and it harmonizes the new system with Igni's existing internal input limits.

**Question 3 — "full" token necessity**
The "full" token is a direct violation of Igni’s foundational "one way to do everything" principle and should be removed. The note attempts to justify it by claiming it "clarifies intent in code," but this is a classic trap. "Clarifying intent" is the exact rationale that traditionally leads to bloated language specifications and multiple valid syntaxes for identical behaviors. 

If omitting a max-width modifier means the layout has no width cap, then introducing a specific token that also means the layout has no width cap creates a branching path. When an LLM is asked to create an unbounded container, it now has to flip a coin: does it omit the modifier, or does it write the "full" token? Furthermore, providing a "full" token opens the door to LLM hallucinations. A model might assume "full" means 100-percent width regardless of parent padding, or it might hallucinate sibling tokens like "auto" or "none" because the presence of "full" implies the existence of a broader semantic CSS-like vocabulary. The strictest, most defensible application of the project's principles is to drop "full" entirely. To express an uncapped layout, the developer (or model) simply does not invoke the max-width modifier. 

**Question 4 — fill constraint composition**
The composition of fill and max-width introduces edge cases that absolutely require explicit spec clarification, primarily concerning leftover space. 

In scenario A, where a child is set to fill available space but capped at tablet width (768 pixels), and the parent is 1000 pixels wide, what happens to the remaining 232 pixels? Does the capped child center itself within the parent’s available space, or does it align to the start? Flexbox defaults usually leave this space at the end unless alignment overrides are in place. The spec must explicitly state default alignment behavior when a layout hits its cap but is instructed to fill. 

In scenario B, where the parent is narrower than 768 pixels, the tablet max-width correctly acts as a no-op, and the element gracefully fills the narrower space. This is standard and requires little clarification.

In scenario C, where multiple sibling layouts are competing for space and all are set to fill, but one has a narrow cap (like "phone"), the spec must clarify the distribution math. Standard flex behavior dictates they share space equally until the constrained sibling hits its 480-pixel cap, at which point the remaining siblings absorb the rest of the available parent width. While this makes mathematical sense, an LLM cannot visually verify this behavior. Therefore, the exact flex-grow redistribution behavior needs to be documented in the spec so that models generating complex multi-column dashboards understand how space shifts when one column locks at its maximum limit.

**Question 5 — Shape C rejection**
The rejection of Shape C and all arbitrary numeric escape hatches is highly defensible and represents the most principled stance in the entire document. If you give an LLM the option to use arbitrary numbers, it will use them, and the token-first philosophy immediately collapses. 

The strongest counter-argument to this rigidity is the reality of designer-to-developer handoff. A designer working in Figma will often specify a card width of exactly 540 pixels or a sidebar of 280 pixels. A human developer will experience friction when they realize the language physically will not allow them to match the design spec, forcing them to settle for 480 pixels or 768 pixels. In many frameworks, this friction leads to developer churn.

However, this counter-argument does not move me because it misinterprets Igni's north star. Igni is not designed to be a pixel-perfect Figma translation layer; it is designed to be highly reliable for LLM generation. To achieve zero-shot LLM accuracy and eliminate variance, you must make blood sacrifices regarding precision. Design systems like Tailwind already force developers to snap to predefined spacing scales, abandoning arbitrary pixel nudging in favor of systemic consistency. Igni simply pushes this philosophy to the compiler level. By holding the line on Shape B, Igni forces the constraint upstream: UI designs will adapt to Igni's token ladder, rather than the language bending to arbitrary design specs. This rigidity is the only way to protect the LLM learnability thesis long-term.

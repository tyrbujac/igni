**Question 1 — Token naming.** An LLM trained on Tailwind/Material/Bootstrap will most readily reach for `sm`/`md`/`lg`/`xl` as breakpoint names — that's the dominant convention by sheer volume of training data. But those names are *abbreviations*, and they collide with what feels like Igni's broader naming aesthetic (`small`/`medium`/`large` spelled out for spacing). If you used `sm`/`md`/`lg` you'd also create a within-spec inconsistency: spacing tokens are spelled out, width tokens are abbreviated. That's worse than picking a slightly less LLM-frictionless name. Of the spelled-out options, `phone`/`tablet`/`desktop` matches Material's documented breakpoint vocabulary closely and is what models reach for in *prose* explanations of breakpoints, even when their *code* says `md`. So in the zero-shot Igni context (no prior Tailwind class in scope), I'd expect `phone`/`tablet`/`desktop` to be guessed reasonably often once the cheatsheet has been seen.

The device metaphor concern is real but I think overstated. The note already addresses it ("the pixel value is the value; the name is a hint"). The genuine awkwardness is reading `max-width: phone` on a sidebar inside a desktop dashboard — it parses as a category error to a human reviewer even though it's mechanically correct. Semantic-purpose names (`card`/`reading`/`wide`) avoid that but trade it for a worse problem: they're Igni-specific vocabulary an LLM has never seen, so cold-test adoption depends entirely on the cheatsheet sticking. Device names lose a small amount of reading clarity in non-device contexts and gain a large amount of LLM prior pull. That's the right trade. I'd ship as proposed.

**Question 2 — Pixel ladder.** 480/768/1200 is reasonable but slightly off on the middle rung. 768 is the iPad-portrait Material/Bootstrap breakpoint; it's well-known but it's a *device threshold*, not a *content width*. Article body width (the canonical "reading column" use case) is conventionally 640–720px (Medium ≈ 680, Substack ≈ 640–720). 768 is fine for that but on the wide side. Modal width is typically 400–600 — `phone` (480) covers it. Dashboard column is 240–320 (sidebar) or 800–1200 (main pane) — `desktop` (1200) covers the latter, nothing covers sidebar. Marketing hero text block is 600–800 — `tablet` works. So the ladder mostly snaps, with one real gap: there's no "narrow content column / sidebar" token below `phone`. I'd resist adding `compact: 360` because the natural use case (sidebars) is better served by a future `width:` (exact, not max) primitive — and the follow-up note already flags that. Adding `wide: 1600` is more tempting for dashboard cinema cases, but I'd hold off until a real app surfaces it; the v0.13 motivation is "cap things smaller than the viewport," not "cap things at a generous-but-bounded desktop width." 4 tokens passes the 3–5 rule and covers the motivating cases. Ship 4, keep 5 in your back pocket.

**Question 3 — `full` token necessity.** This is the sharpest design question in the note and I think `full` should be cut. The "one way to do everything" principle is unambiguous: if omitting `max-width:` and writing `max-width: full` produce identical codegen, you have two valid syntaxes for the same concept. The note's justification — "clarifies intent" — is exactly the kind of soft argument the principle is designed to refuse. Igni doesn't have `padding: none` to "clarify" the absence of padding; it doesn't have `background: transparent` as the canonical no-background. Omission *is* the canonical form across the rest of the spec. Adding `full` here breaks that consistency and gives an LLM a fourth branch to guess wrong on (it might write `max-width: full` when no modifier was needed, then a maintainer wonders if the explicit form has different semantics). The strongest case *for* `full` is documentation: a reviewer scanning a layout sees `max-width: full` and knows the author considered the question. That's a real benefit but it's a comment-shaped benefit, not a syntax-shaped one. Cut `full`, ship 3 tokens, note in the cheatsheet that "no `max-width:` = uncapped" is the way to express it.

**Question 4 — `fill: true` × `max-width:` composition.** The semantics genuinely need spec text because the obvious reading isn't fully obvious. (a) Parent wider than 768: the layout caps at 768 and the parent's remaining space goes unused — this is correct behaviour but it raises the immediate follow-up "where does the capped layout sit within that unused space?" The answer has to be spelled out: presumably it follows the parent's `align`, but if the parent is `layout horizontal, spread:` with one capped child and one uncapped child, the spread semantics get strange. (b) Parent narrower than 768: max-width is a no-op, the layout takes the parent's width — uncontroversial, but worth saying. (c) Multiple `fill: true` siblings where one has `max-width:` — this is the actual ambiguity. Flutter's `Expanded` with a `ConstrainedBox` child distributes flex first, then constrains, which means the capped sibling can end up *narrower* than its cap while uncapped siblings absorb the slack. Or the implementation could distribute slack so the capped sibling hits exactly its cap and the others split the rest. Both are defensible; they produce visibly different layouts. The spec needs to pick one and say so. I'd recommend: max-width caps the sibling, uncapped `fill: true` siblings absorb the remainder proportionally to their flex weight. Also worth clarifying: does `max-width: tablet` without `fill: true` still expand to fill (capped at 768), or does it shrink-wrap to content (capped at 768)? Flutter's default is shrink-wrap; users coming from CSS expect expand. Pick one, document it.

**Question 5 — Shape C rejection.** The rejection holds and I'd defend it strongly. The strongest counter-argument is the designer-handoff case: Figma spec says "card width 540px," developer types `max-width: tablet` (768), result is visibly wrong by 228px, designer files a bug, developer either lives with the wrongness or hand-edits the generated Dart. Repeated enough times, this drives churn away from Igni toward a tool that respects the spec. That's a real failure mode. It doesn't move me because: (1) the same designer-handoff problem exists for *every* token system — Tailwind users have been picking `max-w-md` (448) for "540px" specs for years and the ecosystem hasn't collapsed; (2) the fix when it actually bites is not a numeric escape hatch but a richer token ladder, which preserves the variance-elimination property; (3) admitting numerics for "the 8%" guarantees LLMs use them for the 92% too, because numeric is the path of least resistance in their training distribution — you'd lose the token discipline entirely within two model generations. The token-first thesis is load-bearing or it isn't; a partial commitment is worse than either pole. If a controlled escape hatch ever becomes necessary, the right shape isn't `max-width: 540` but a separate, deliberately-ugly primitive (`max-width-px: 540` or similar) that's syntactically marked as the exception path — making it costly enough that LLMs and humans both prefer tokens. But I wouldn't ship that pre-emptively; wait for Stage 3 to falsify the prior first.

**1 — FLIP (anti-anchoring)**. The strongest case against option (b) is that it permanently hardcodes a binary presentation state (`light` vs `dark`) into the AST, violating the "spec budget" by introducing top-level structural syntax for what is fundamentally a semantic data matrix. At a v1.0 horizon, enterprise apps require generic theming axes: high-contrast, density, sepia, or multi-brand white-labeling. Option (b) closes off these generic use cases because the parser only knows the hardcoded keyword `dark`. It also weakens the "No magic" invariant: under (b), a static reference like `color: brand` in UI code is no longer a transparent pointer to a constant, but an implicit runtime closure (`getColor(brand, context.isDark)`). Shipping (c) now—expanding the semantic token bag—would maintain the strict 1:1 token-to-value compile-time invariant, deferring complex matrix-state-resolution to a proper, generic `modes:` primitive in v0.21+ rather than burning AST surface area on a one-off "dark mode" keyword. 

**2 — REFINE**. (b.iii) as a tri-state boolean (`null`, `true`, `false`) is LLM poison. In zero-shot generation, models inherently treat booleans as binary and will confidently write simplistic toggle logic like `shared.dark_mode = !shared.dark_mode`. If the state is `null` (follow OS), negating it either throws or resolves to `true` (breaking the toggle loop), permanently destroying the user's ability to revert to the OS default without explicit, verbose ternary checks. To preserve lexical reactivity and LLM accuracy, the selector mechanism must be an explicit enum: `shared.theme_mode` with literal states `system`, `light`, and `dark`. This enforces the "one way to do everything" rule, removes ambiguous tri-state logic, and cleanly triggers the top-down re-evaluation inherent to Igni's reactivity model whenever the enum is reassigned.

**3 — FLIP**. The recommendation for (c.i) strict-pair composition violates the "spec budget" optimization for output verbosity and will cause immediate LLM hallucination friction. In a standard Figma auto-layout file with 25 color tokens, ~18 primitive palette colors (e.g., `brand_500`, `neutral_100`) remain completely static; only ~7 semantic aliases (`surface`, `text_primary`) actually invert. Strict-pair forces the developer (or LLM) to blindly duplicate unchanged static values across both blocks, bloating the code and creating a maintenance hazard where a change in the light palette is forgotten in the dark palette. Auto-fallback (c.ii) is the only discipline that maps to "Default/Light" as a base layer and "Dark" as a sparse override layer, radically reducing zero-shot output length and correctly mirroring the variable cascade behavior of both CSS and Figma.

**4 — REFINE**. Mixing structural defaults (`appbar_background`) and semantic colors (`brand`, `surface`) in the same `theme: color:` bag breaks LLM pattern recognition and violates the "One way to do everything" principle. A color token is a raw value a component *consumes*; an AppBar default is a configuration of the *component itself*. If the cheatsheet teaches that `appbar_background` lives in the `color:` bag, LLMs will inevitably attempt to invent non-color structural tokens there, like `button_radius` or `card_padding`. To cleanly define the structural-vs-semantic boundary, semantic colors belong in `theme: color:`, but structural chrome defaults should be strictly isolated to their own namespace (e.g., preserving `theme: appbar:` from Option A alongside `color:`). This keeps the color bag homogeneous and prevents LLMs from hallucinating component structural overrides as global hex variables.

**5 — HOLD**. Committing to the forward-coupling rule ("token references resolve to the active variant's value") now is architecturally vital. If dark mode changes token resolution for colors but not for borders, the language's mental model fractures. The pressure test regarding future `shadow:` requirements actually reinforces this hold: shadows *do* require physically distinct properties in dark mode (heavier spread/elevation to remain visible against dark surfaces). If we establish the active-variant-resolution invariant now, it guarantees that a future `theme dark: shadow: elevated:` block can seamlessly override the light mode shadow definitions without friction. Laying down this rule in v0.20 establishes that the active variant governs the entire theme resolution context, ensuring v0.21's shadow implementation inherits a clean, predictable routing path without conflating color switching with elevation.

**6 — REFINE**. The design note completely misses the critical intersection between global variant switching and the newly shipped v0.19 animation primitives (`transition: fade`/`slide`). When the theme mode reassigns and lexical reactivity triggers a top-down screen re-evaluation, does the UI instantly snap, or does it crossfade? In modern environments, theme switches are beautifully animated. If the spec text locks without addressing this, we introduce "magic"—either an un-configurable default snap, or an implicit crossfade that the developer cannot control or trace in the source. Before v0.20 locks, the spec must definitively answer whether the `transition:` keyword can be applied to the top-level `theme:` block to govern active-variant switching, or explicitly declare theme switching as instantaneous for this minor version to preserve rule simplicity.

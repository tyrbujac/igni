# Stage 2 Review: v0.20 Dark-Mode Propagation

## Q1 — Strongest case AGAINST option (b)

**Position: refine** — (b) survives but the case against it is stronger than the note acknowledges, and it should be acknowledged in spec text.

The load-bearing invariant (b) weakens isn't the compile-time-token rule (the note correctly reframes that). It's the **"no magic"** principle: with (b), a screen renders differently based on a runtime selector that *isn't visible at the call site*. A user reading `Card background: surface` cannot tell from the source whether `surface` is `#F5F5F5` or `#0D0D14` — the cause is in `MediaQuery` or `shared.dark_mode`, neither of which appears in the component invocation. Options (a) and (c) keep this property: tokens are static, what-you-read-is-what-you-render. (b) introduces the first piece of true environmental indirection in the language. The strongest argument for shipping (a) at v0.20 and deferring selection: dark mode has *two* real-app instances; runtime *toggling* has one (Gemini-3-flash's `if shared.dark_mode:`). Boojy's gap is solvable by (a) alone — its problem was "no AppBar override path," not "OS appearance changes mid-session." Shipping (a) at v0.20 closes 2-of-2 observed gaps with the smallest spec budget; v0.21 can add `theme dark:` once the selector design has had a cycle of pressure-testing alongside accessibility (which will need the same selector machinery). The cost of deferring: one wasted cycle if v0.21 instances confirm (b) anyway. The cost of shipping (b) now: a runtime-selector design done under v0.20 time pressure becomes load-bearing for a11y, high-contrast, and large-text in v0.21 — getting it wrong is expensive. **This isn't enough to flip the lean, but the spec text should explicitly name the no-magic tension** and document that variant selection is the *sole* sanctioned environmental indirection — otherwise the precedent leaks.

## Q2 — Runtime selector mechanism

**Position: refine** — (b.iii) is right in shape but the tri-state has an LLM-authoring gap.

(b.iii) composes correctly with lexical reactivity in the obvious case: `shared.dark_mode` is a `shared` variable, screens that reference theme tokens transitively reference it via the resolver, reassignment triggers re-render. That's the right semantic and it falls out of existing rules. The OS-appearance path is trickier — `MediaQuery.platformBrightnessOf` isn't a `shared` variable, so the lexical-reactivity story needs a named extension: "OS appearance is treated as an implicit reactive dependency for any screen that references a theme token." Spec text must say this; otherwise an LLM will write a "refresh on appearance change" workaround. The tri-state (`null`/`true`/`false`) **is** the gap I'd flag: three states with one being `null` is exactly the shape models drop. Concrete failure mode: model writes `shared.dark_mode: false` as the initial value (meaning "force-light") when it intends "follow-OS," and the toggle never returns to OS-tracking. **Refinement: replace the tri-state boolean with an explicit three-value enum** — `shared.theme_mode: auto | light | dark` (default `auto`). Three named states beat two booleans-with-null on LLM accuracy every time, and it costs one keyword. Per-route override and programmatic animation are out-of-scope for v0.20 but the selector design should not foreclose them: a screen-local `theme_mode:` override block in v0.22+ should compose with the global `shared.theme_mode` without rework. Deferred-load themes (network-fetched palettes) are out of scope and should stay so — that's a real-app signal Igni hasn't seen.

## Q3 — User-defined token composition with dark variant

**Position: flip** — recommended lean is (c.i) strict pair; I'd ship (c.ii) auto-fall-back with a lint warning.

The Figma-file empirical question is the decider. In a typical 23-token palette, **roughly 4–7 tokens have genuinely distinct dark values** — surfaces, scaffolds, default text, maybe one or two elevated cards. Brand colors, accent colors, semantic colors (success/warning/error), and most decorative colors are identical or near-identical across modes. Strict-pair forces the user to redeclare 16+ tokens identically, which is exactly the kind of mechanical duplication the language should refuse to demand. Worse, strict-pair teaches the wrong mental model: it implies dark mode is a *full repaint* when it's actually a *targeted override*. The invisible-bug risk the note raises is real but lint-tractable: `lint-spec-trio` (Workstream C, shipping the same cycle) can warn on tokens used as a `background` or `scaffold:` source that don't have a dark variant — that's the actually-dangerous case. Brand-token fall-back is fine and expected. **Refined rule: dark variant inherits light by default; lint warns when a non-dark-overridden token appears in a structural-chrome position.** This also aligns with Figma's modes semantic — Figma variables fall back to default mode when a mode-specific value isn't set; it doesn't force pair-completeness. Strict-pair would be design-by-reinventing exactly where Path C says don't.

## Q4 — Default-text override scope and the structural/semantic boundary

**Position: refine** — the lean (d.i, all text) is wrong for the same reason (c) is weakest: bag heterogeneity. But splitting blocks is over-correction.

The note's own Stage-0 risk against option (c) — "scaffold_background is a different *kind* of token than brand" — applies just as forcefully to option (b) if structural and semantic tokens cohabit `theme: color:`. The cheatsheet has to teach "these tokens are user-defined and you reference them" alongside "these tokens are reserved names with framework semantics" in the same block, and that's two rules in one shape. But splitting into `theme: color:` + `theme: chrome:` adds a top-level structural distinction that itself becomes a guess-point. **Better refinement: keep one block, but reserve a fixed, small, named set of structural tokens with a documented prefix or convention.** Concretely: `scaffold:`, `appbar:`, `default_text:` as reserved sub-blocks *inside* `theme:` (this is option (a) machinery), and `theme: color:` stays purely user-defined. So the shape is `theme: color: brand: ...` (user tokens) + `theme: scaffold: background: card` (structural), and `theme dark:` mirrors both. This is option (a) ∪ option (b) — not in the trilemma as stated. The cheatsheet teaches: "color: is your palette; scaffold:/appbar:/text: are framework chrome." Two rules, two shapes, no overlap. On (d.i) vs (d.ii): default text scope should be (d.ii) **structural text only** — overriding *all* text colour from the theme block produces unfixable cascade problems when a Card's body wants its own colour. Per-component `color:` always wins; the theme provides chrome defaults.

## Q5 — Forward-coupling with `border:` and future `shadow:`

**Position: flip** — the lean is "commit now"; I'd defer.

Active-variant resolution is correct for *colour* tokens referenced from `border:` — `border: thin, color: subtle` should absolutely flip when the theme flips. That's not the question. The question is whether the *rule* "token references resolve to the active variant's value" extends to *non-colour* tokens, and that's where v0.21 `shadow:` will hurt. Shadows in dark mode aren't just darker shadows — they're often *lighter* (subtle highlights from above) or use coloured glows instead of black drop-shadows, because dark-on-dark shadows are invisible. If `shadow:` ships preset levels per Path C (`thin/medium/thick`), the elevation token is a *physical-layer* concept, not a colour-resolution concept — the dark variant of `shadow: medium` may need a fundamentally different blur/spread/colour structure, not just a recoloured version of the light shadow. Committing the resolution rule now bakes in "colour-substitution" semantics that v0.21's design will want to escape from. **Refinement: commit the rule narrowly — "colour token references in `border:` resolve to active variant" — and explicitly leave `shadow:` and other future visual-chrome primitives unspecified.** Cost of deferring: one sentence of spec ambiguity. Cost of committing: v0.21 ships either a constrained shadow design or a rule-breaking exception, both of which are worse than ambiguity.

## Q6 — Load-bearing concerns the note misses

**Position: refine the framing — bundling is wrong, scope is wrong.**

Three things the note doesn't address that should be settled before spec text locks. **First and largest: a11y is in v0.21 and dark-mode is in v0.20, but they share the same selector machinery.** High-contrast mode, large-text mode, reduced-motion are all "user/OS preference selects between static variant sets" — structurally identical to dark mode. Designing the v0.20 selector for dark-mode-only and then retrofitting a11y in v0.21 is the classic mistake; the selector mechanism should be designed *generically* now (`shared.theme_mode`, `shared.contrast_mode`, `shared.motion_mode` all routing through one resolver) even if only `theme_mode` ships in v0.20. Otherwise v0.21 a11y reopens v0.20's selector design. **Second: theme transition animation.** v0.19 just shipped `transition: fade/slide`. Users will expect `theme_mode` flips to animate — and the spec is silent. Either commit "theme switches are instant, no transition" (defensible: matches SwiftUI default) or design the transition story now. Don't leave it ambient; the first user who tries `transition: fade` on a theme switch will produce a workaround. **Third: bundling.** Workstream A (dark-mode + runtime selector + new top-level grammar + MaterialApp integration) is bigger than B (token additions) and C (lint tooling) combined. The note's Trigger B (>3 sessions = partial) is the right instinct but the wrong threshold — I'd argue dark-mode propagation alone merits v0.20-as-its-own-cycle, with B and C deferred to v0.21. The risk in bundling: if dark-mode hits a design surprise in implementation, B and C get dragged into a "v0.20 partial" that fragments the cheatsheet. **Recommendation: split. Ship dark-mode as v0.20, bundle B+C into v0.20.5 or v0.21, and use the gap to pressure-test the selector design against a11y before it locks.**

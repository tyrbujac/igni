1. **Q1 — HOLD, but the strongest case against (b) is real.** Option (b) weakens a load-bearing invariant: Igni currently has a clean separation where `theme:` is static data and runtime behavior is visible in ordinary source. With `theme dark:` plus OS/`shared.dark_mode` selection, theme tokens become an implicit runtime dependency: a screen may change because the platform brightness changed even though the screen source never mentions brightness or `shared.dark_mode`. That is a small but genuine “magic” leak. At a v1.0 horizon, (b) also risks turning Igni’s theme system into a second reactive subsystem with special global rules, special reserved shared state, and future pressure for more modes: high contrast, sepia, brand themes, per-route theme islands, preview panes showing light/dark side by side. The real-app shape (b) potentially closes off is **local explicit theming**: a settings screen that previews light and dark cards simultaneously, an embedded document that must stay light, or a route that intentionally differs from the app-wide theme. Options (a)/(c) preserve dumb static tokens and leave local composition open because users can still pass explicit colors or use separate structural settings. The strongest reason to ship (a) in v0.20 is: it fixes Boojy’s immediate AppBar/scaffold gap with minimal language debt, preserves the v0.18 compile-time rule perfectly, and buys one release of real-app signal before committing to a global runtime selector. I still converge with (b), because the observed failure is not merely missing AppBar tokens; it is missing active-theme selection. But the cost is an architectural one, not just implementation size.

2. **Q2 — REFINE.** I agree with (b.iii) — OS-following plus user override is the right product semantic — but the selector must be specified as one global app-level mechanism, not an open-ended theming API. Per-route overrides, programmatic theme animation, deferred-loaded themes, and side-by-side previews should be explicitly out of v0.20; otherwise this becomes a general theme engine instead of a dark-mode primitive. Lexical reactivity composes if the spec says: any component/screen that references a theme token implicitly depends on the active theme variant, so OS brightness changes or `shared.dark_mode` reassignment invalidate those readers. That is the right semantic, but it must be named because otherwise it looks like spooky action at a distance. The tri-state `shared.dark_mode` shape is acceptable but slightly awkward: `true = dark`, `false = light`, `null = system` is compact, but a nullable variable named `dark_mode` invites LLMs to write ordinary `if shared.dark_mode:` logic and forget the system state. I would keep the tri-state for spec-budget reasons, but require the cheatsheet to teach exactly one canonical toggle pattern and forbid ad hoc runtime theme conditionals inside `theme:`. If the team can afford one extra named concept, `shared.theme_mode: system | light | dark` is clearer, but it adds enum/string surface and typo risk; I would not take that unless tri-state failures appear in real apps.

3. **Q3 — HOLD, with one wording refinement.** Strict-pair is the right discipline: if `theme dark:` exists, every user-defined color token declared in light should be declared in dark, and vice versa. I would make this a compile/spec validation error rather than literally a parse error, because the parser should not need cross-block semantic knowledge. The friction is real: many brand tokens will be identical across light and dark, so users may have to repeat `brand: "#80CBC4"` twice. But that explicit duplication is better than invisible fallback, because fallback creates exactly the bug dark mode is meant to avoid: a designer forgets to define `card` or `subtle_border` in dark mode and the app ships a light-mode surface inside a dark shell. Figma’s model also supports strictness: variables have values per mode, even when the value is the same. In a real 23-token Figma file, I would expect perhaps 14–19 tokens to differ — surfaces, text, borders, muted states, dividers, error backgrounds — and 4–9 to remain identical, mostly brand/accent colors. Repeating those identical values is acceptable Igni verbosity because it removes ambiguity and gives LLMs one canonical rule: dark mode is a full token set, not a sparse patch.

4. **Q4 — REFINE.** I would not put component-specific names like `appbar_background` beside user tokens like `brand`, `card`, and `surface_elevated` in the same undifferentiated `theme: color:` bag. That heterogeneity hurts LLM adoption because the model cannot infer whether `color:` contains palette tokens, semantic roles, component chrome, or all of the above. The better shape is option (b) for variants plus a small structural split inside each variant: `theme: color:` remains the reusable color-token namespace, while structural chrome lives in explicit sub-blocks such as `scaffold:` and `appbar:` whose values reference color tokens. That borrows the clean part of option (a) without losing runtime selection. For default text, I would avoid a vague `default_text` token if possible and specify one canonical semantic role, e.g. `text` or `on_surface`, whose scope is “all text without an explicit color.” AppBar foreground can then be structural: `appbar: foreground: text` or `foreground: on_surface`. The cost is a slightly larger grammar than pure (b), but it preserves the structural-vs-semantic boundary and makes the cheatsheet clearer: colors are tokens; scaffold/AppBar are chrome consumers of tokens.

5. **Q5 — HOLD, but scope the commitment carefully.** The rule “token references resolve to the active variant’s value” should be committed now, because it is foundational to dark-mode propagation. If `border: thin, color: subtle` references `subtle`, then `subtle` must late-bind to the active light/dark value; otherwise users are back to manual per-widget dark-mode annotations. This does not need to constrain v0.21 `shadow:` design if the rule is phrased generally: references to theme tokens resolve through the active variant; the future shape of shadow/elevation tokens is not fixed. If v0.21 ships `shadow:` presets like `thin`, `medium`, `thick`, those presets can themselves be variant-defined. In light mode, `shadow medium` might be a grey blur with lower opacity; in dark mode, it might use a different blur/spread/opacity or even a lighter edge treatment. Active-variant resolution helps that design rather than blocking it. The thing to avoid is saying “shadow levels are just colors” or forcing shadows to reuse color-token semantics. Commit to late binding across variants, not to a specific future shadow ontology.

6. **Q6 — REFINE.** The design note is directionally right, but it should lock a few missing v1.0-horizon constraints before spec text lands. First, define behavior when `theme dark:` is absent: does the app ignore OS dark mode and stay on `theme:`, or does codegen synthesize defaults? I would say no synthesis; absence of `theme dark:` means one static theme. Second, snapshot testing needs a dark-mode hook in v0.20, otherwise Workstream A and v0.19’s snapshot work do not compose; something like `mock brightness: dark` or equivalent should be considered part of the feature, not a later convenience. Third, accessibility must be explicitly non-blocked: dark mode is a color-scheme axis, not the general future mechanism for high contrast, reduced motion, or large text. Do not overgeneralize `theme dark:` into arbitrary modes yet, but avoid wording that makes binary light/dark the only possible future adaptive theme axis. Fourth, theme transitions should not be automatic despite v0.19 animation support; automatic cross-fades would violate “no magic.” If users want animated theme changes later, that should be visible in source. Finally, the bundling with spacing tokens and lint-spec tooling is acceptable only if (b) stays narrow and the lint work enforces the new invariants: strict token pairs, no runtime conditionals inside `theme:`, and canonical `shared.dark_mode` usage. If selector semantics or chrome-block shape remain unsettled after review, I would split Workstream A into its own minor cycle rather than ship a half-specified runtime primitive.

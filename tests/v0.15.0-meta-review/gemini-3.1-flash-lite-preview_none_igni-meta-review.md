### Q1 — Strengths
The project’s greatest strength is its **uncompromising commitment to an LLM-centric "spec budget."** Most languages suffer from "feature creep" that introduces accidental complexity; Igni treats every new keyword as a tax on the LLM’s zero-shot capability. The convergence between the documents is remarkable: the *README* acts as a sales funnel for the *Spec*, and the *CLAUDE.md* acts as the enforcement mechanism to ensure the *Spec* remains lean.

The most coherent design choice is the **"lexical reactivity" rule.** By defining reactivity as "the screen re-evaluates from the top whenever any referenced variable is reassigned," you unify local state, shared state, and async fetch results under a single mental model. This significantly reduces the training surface for an LLM—it doesn't need to learn a library of hooks or wrappers; it only needs to understand the scoping of variable references. The alignment across docs is strong here: the spec provides the rule, the CLAUDE.md provides the enforcement policy, and the README provides the marketing rationale.

### Q2 — Weaknesses
There is a notable **friction between "no magic" and the "implicit behavior"** of certain primitives. For example, the spec says "no magic," yet the `every <duration>:` block has specific, non-obvious lifecycle behaviors (missed ticks are not replayed; timers pause when not visible). This is "hidden" runtime behavior that an LLM might easily get wrong.

Furthermore, the **"one way to do everything" rule is violated by the current handling of `fetch` mutation vs. read.** The spec claims a unified reactive model, but then introduces a bifurcation: `fetch` at the screen-body level is reactive, while `fetch` inside a function is imperative. This is a subtle trap for an AI assistant. The prose in the *Spec* ("UI primitives only render in screen or component bodies...") is excellent, but it feels like it is patching a hole rather than describing a fundamental symmetry. Additionally, the `theme:` resolution model is somewhat hand-wavy regarding multi-file merging—"last-declaration-wins per token"—which invites conflict if multiple files declare different hex values for the same token key.

### Q3 — Genuine Semantic Uncertainties
1. **Partial re-renders in `each` loops:** The spec says `each` builds a lazy `ListView.builder` for performance, but it is silent on whether a modification to one item causes the entire list to re-render (which would be computationally expensive) or if there is a diffing mechanism. If I am an LLM generating code for a list of 1,000 items, I don't know if I need to worry about performance when I call `replace()`.
2. **`shared:` variable merging:** The spec says all `shared:` blocks merge into a single namespace. If `auth.igni` and `cart.igni` both define `shared: user = null` and `shared: user = "Tyr"`, is that an error? Does the transpiler catch this conflict? The doc says "defining the same name in two different `shared:` blocks is an error," but does not specify how the transpiler handles this in a multi-file project.
3. **`emit` payload serialization:** The spec allows `emit X {email: e, name: n}`. If I want to pass a complex object (like a class instance or a deeply nested JSON object), what are the constraints? Can I pass a `List` of `Objects` via `emit`?
4. **Lifecycle of `fetch` inside `every`:** If an `every 30s` block performs a `fetch`, and the fetch takes 5 seconds, what happens if the next 30-second interval starts before the first one completes? Does it queue? Abort? The spec suggests it’s the "canonical shape," but the concurrency implications are silent.

### Q4 — Recommendations
1. **Standardize the "Mutation" pattern (High Leverage):** The current `fetch` mutation pattern (`saving = true`, `result = fetch(...)`, `saving = false`) is verbose and feels like "the old way." I would introduce a `mutate <url>, method: ...` keyword or a formal `mutation:` block that automatically handles the loading/error state scaffolding. This would move this logic out of the user's manual control and into the compiler, eliminating an entire class of "missing state update" bugs.
2. **Strict Namespace/Shared Validation:** Update the CLI to perform a "global namespace sweep" before transpilation. If a shared variable name is defined in two different files, the error should point explicitly to both file locations. This makes the "shared state" feature robust for large projects.
3. **Clarify `every` concurrency:** In the next version of the spec, explicitly state that `every` blocks are "non-overlapping" (if a task isn't done, the next tick is skipped) or "queued." This removes ambiguity for LLMs generating periodic tasks.
4. **The "Cookbook" is missing:** The project relies on the *Spec* to do heavy lifting. I recommend creating a *Cookbook* repository (or section) that contains the 10 most common Igni patterns (e.g., "The Loading State Pattern," "The Trigger-Variable Pattern," "The List-Rebuild Pattern"). Moving these out of the *Spec* and into *Cookbook* will clean up the *Spec* by removing "tactical patterns" and letting it focus solely on language syntax and reactivity rules.

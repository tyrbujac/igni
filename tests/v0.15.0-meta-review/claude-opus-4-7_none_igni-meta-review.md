# Review of Igni v0.15.0

## Q1 — Strengths

The strongest thing about Igni is **the coherence between its stated method and its actual artefacts**. Most "language designed for LLMs" projects are vibes; Igni has a measurable feedback loop (cold-LLM panels, numbered convergence signals like "11/14 cumulative" on the v0.15 widening), a versioned trap journal, and visible scars from the loop in the spec itself. The README's "9/9 frontier adoption of `{target with ...}` unprompted" claim is the kind of thing most language projects can't make. Reading CLAUDE.md after the spec, the `with`-syntax design rationale ("braces are required" because "object construction lives inside `{}` everywhere else") clearly came from the same discipline that produced the test methodology — not retrofitted.

Specific design choices pulling real weight:

**The `shared.X` prefix as visible coupling marker.** This is the single best decision in the spec. Most reactive systems either hide globals (Redux selectors, Vue's `provide/inject`) or force ceremony (React Context boilerplate). Igni's rule — local by default, `shared.` at every read/write site — gives you the coupling X-ray without any tooling. It composes cleanly with the lexical reactivity rule and is the kind of thing an LLM gets right zero-shot because there's no alternative form to pick wrong.

**Lexical reactivity stated as one sentence.** "Each screen re-evaluates from the top whenever any variable it lexically references is reassigned." That's the entire model. The spec keeps refunding this rule — `every`, `fetch`, `shared`, `on change` all collapse back into it. The fact that "derived state needs a function, not a top-level `=`" falls out of the rule rather than being a separate feature is genuinely elegant.

**The reactive-fetch footgun being a *transpile error* with a fix-it.** This is where the LLM-orientation pays off most concretely. The model reaches for `fetch("/api/search?q=" + query)` because that's the obvious thing; the language stops it and points at the trigger-variable pattern. This is the right level for "guardrail" — not a stylistic warning, not a runtime bug, a parse-time refusal. The v0.15 extension to `locate()` shows the rule is generalising correctly.

**Cross-document reinforcement.** CLAUDE.md's "spec is a budget, not a backlog" lands harder once you've read the spec and seen `max_width:` deliberately offering only `phone/tablet/desktop` with no escape hatch. The README's "Igni is not for creative tools" lands harder once you've read the spec and noticed there's no animation system, no gesture lifecycle, no canvas. The three documents agree on what Igni *isn't* — that's rarer than agreement on what it is.

**The "honest no" framing in CLAUDE.md.** The instruction that Claude correctly refusing to invent around a gap is *more valuable* than a clever workaround is unusually self-aware for an agent doc, and it visibly shapes the artefacts (e.g. the each-loop bind rejection being preserved rather than papered over).

## Q2 — Weaknesses

**The spec's tone is uneven and the changelog-paragraph at the top of the spec violates CLAUDE.md's own rule.** CLAUDE.md says: "Teach the language first; don't open with release notes... Keep the opening stable across future versions." The v0.15.0 spec opens with a 200-word "Changes from v0.14.0" paragraph that is denser than the *Hello World* section that follows, mentions `docs/private/96`, "11/14 cumulative signal", and "Pomodonut criterion-4 #2 close gates" — none of which a first-time reader can parse. This is exactly the failure mode the agent doc warned against. It's the most prominent prose in the canonical spec and it's targeted at the design-process audience, not the language-learning audience.

**"One way to do everything" has visible exceptions that the spec doesn't quite own.** `bind: shared.X` works on `slider/toggle/checkbox/dropdown` but not `input`. The bridge pattern (local var + `on change:` writeback) is a *second way* to do the same thing — and it's now the only way for `input`. Each-loop field access is a third asymmetry. The justification ("`TextEditingController` needs a stable Dart identifier") is an implementation leak being surfaced as a language rule. The spec is honest about this but it's a real cost: an LLM learning Igni now has to remember which primitives accept which form of `bind:`. The Property Applicability appendix doesn't capture this asymmetry.

**The Todo example claims "every line load-bearing" but `items = items + [{text: draft}]` is doing two things at once** — list append and object construction. A first-time reader has to recognise both simultaneously. More importantly, the screen-internal function `add():` is introduced 17 lines into the spec without explanation; "Don't worry about concepts you haven't met yet" pushes work onto the reader for which I don't think the payoff justifies the cost. The Counter example three sections later is the better introductory example and probably should come first.

**The multi-view screens "tactical pattern" undermines the navigation story.** Section gives a 40-line example of using `if`/`else` at the screen body level to swap views inside one screen, with caveats about when not to use it. This is the spec offering a second way to do navigation, with prose hedging — exactly the kind of thing the budget rule was supposed to prevent. The pattern exists because real navigation is underspecified (no deep links, no modal stacks, no back-stack control listed in tracked open questions). The spec is inviting users to route around its missing features. I'd cut this section or move it to the cookbook.

**The `count(list, target)` vs `length(filter(...))` distinction is a sharp edge.** The spec acknowledges this — "count is for counting exact-value matches" — but the reasoning ("count doesn't accept a predicate") is more rule-stating than rule-justifying. Why does `find` accept a predicate but `count` doesn't? An LLM that learns "`count` counts matches" will write `count(alerts, a => a.level is "critical")` and silently get 0. The compile-time rejection mentioned in the README helps, but the language inconsistency itself is the smell.

**The README's installation story doesn't match the "research prototype" framing.** The instructions for symlinking onto PATH, requiring Flutter SDK + Node 18+ + Chrome, and the unspoken expectation that `flutter create` works on first run, all read like a tool inviting external users. Then the Status section says "single-author by design during early access... external contribution will open post-v1.0." Pick one — either ship it as something to try, or frame it as a dissertation artefact people can read but probably shouldn't install. Right now the README does both and the seam shows.

**CLAUDE.md is trying to be three documents.** It's an AI-assistant onboarding doc, a design-principles digest, and a working-with-Tyr style guide. The "Tracked open questions" section duplicates ROADMAP material; the "ROADMAP tiering" section is project-management process; the "non-negotiable design principles" are spec-essential and would be load-bearing for any reader, not just an AI. Splitting into PRINCIPLES.md (visible to humans + AI) and CLAUDE.md (working contract) would lose nothing.

## Q3 — Genuine semantic uncertainties

1. **What happens when `every 1s:` reassigns a variable that no UI reads?** Reactivity is defined as "screen re-evaluates when any variable it *lexically references* is reassigned." If `every 1s: tick = now()` runs and nothing in the layout reads `tick`, does the screen re-render? The rule says no — but then `every` blocks become pure side-effect channels that the user might assume drive UI. The Pomodonut example always reads `tick` indirectly via `remaining(...)`, so the question is dodged.

2. **Does `is` use reference identity or value equality on primitives?** The spec says "Object identity is reference-based, not structural" but only in the context of object literals. For `count is 0`, `name is "Tyr"`, `op is "+"` it must be value equality — these are clearly the intended uses. For lists? `items is []` — what does this do? For two strings constructed differently — `("hello " + name) is greeting` — is this guaranteed? The spec implies value-for-primitives, reference-for-objects, but never says it.

3. **What does `is in` do for objects in a list?** "By identity match (the same equality `is` uses)." If `is` is reference-equality for objects, then `product is in shared.cart` only works if `product` is the *exact* reference that was added — which is true if you added it from a `each product in products` loop, but not if `product` was reconstructed from a fetch. This is a real gotcha and I can't tell from the spec whether `find(list, target)` and `is in` use `===` semantics or some kind of structural-with-id-field shortcut.

4. **Can `each` iterate over a string or a number range?** `each c in name:` — does this iterate characters? The spec only shows `each` over lists. Given there's no `range()` builtin shown, how does an LLM write "do this 5 times"? `each i in [0,1,2,3,4]:`? Functions can have loops but functions don't have `each`-with-index — the iteration variable is the item, not (item, index). For "delete button labelled with row number" you can't write the row number.

5. **Are functions inside `each` re-evaluated per item or hoisted?** `each item in items: label total(item)` — does `total` re-run for every render of every item, every reactivity cycle? Components "re-evaluate with their parent" but functions called from layouts aren't components. With paginate: 20 the question gets sharper — is the function called only for visible items?

6. **What's the type of `tick = now()` minus another `now()`?** The spec says `now()` returns "an integer count of seconds since 1970-01-01 UTC." Subtraction works, fine. But `round(elapsed_seconds, 1)` returns a *string*. What does `if elapsed >= dur:` do where `elapsed` is the result of `round()`? The Pomodonut example uses `elapsed = t - start` directly, avoiding round, but the question of "when does string vs number bite me" is unspecified.

7. **What does `fetch` return for non-JSON responses?** All examples assume JSON-decoded objects (`forecast.temperature`, `user.name`). What about `fetch("/api/health")` returning `"OK"`? Or a 204? Or HTML? The spec gives loading/error/loaded but doesn't say what "loaded" looks like for non-JSON. For an LLM building anything beyond example apps, this is a guess.

8. **How does `bind:` interact with computed/derived values?** `bind:` requires an "lvalue" — a simple identifier or `shared.field`. Can you bind to `items[0].name`? The spec rejects this for each-loops but doesn't say whether direct indexing access is OK or not. `slider bind: shared.volumes[0]` — error or success?

9. **What's the precedence of `is in` vs `and`/`or`?** `if product is in cart and quantity > 1:` — does this parse as `(product is in cart) and (quantity > 1)` or as `product is in (cart and (quantity > 1))`? The spec lists boolean operators but not their precedence relative to `is` / `is in` / `is not in`. In practice every reasonable language parses this the natural way, but the spec doesn't pin it.

10. **What happens to in-flight `fetch` when its dependencies change?** If `query` changes and triggers a re-fetch, what happens to the *previous* fetch that was in flight? Cancelled? Ignored on completion? Race-conditioned? An LLM writing a search box wouldn't know whether to add debouncing or trust the runtime. The trigger-variable pattern hides this, but the underlying model is unspecified.

11. **Component re-evaluation with `each`.** "Components re-evaluate with their parent" — does this mean `each post in posts: PostCard post` rebuilds every PostCard on any reactivity tick, even when `posts` itself didn't change? With paginate and 1000 items, this matters a lot. The spec acknowledges no memoisation but doesn't pin the cost model.

12. **`navigate to` semantics on the screen stack.** Does `navigate to Profile user` push or replace? Does `navigate back` from a screen entered via `navigate to` always work, or only sometimes? What happens if there's nothing to go back to? The README mentions "no deep links, query params, modal stacks, back-stack management" as deferred, but the basic stack model isn't stated either.

## Q4 — Recommendations

**1 (highest leverage) — Move the v0.15 changelog paragraph out of the spec opening, into CHANGELOG.md.** Replace it with a one-sentence delta. CLAUDE.md already prescribes this and the spec is in violation. Cost: 30 minutes. Benefit: the canonical document stops opening with material that's incomprehensible to first-time readers and makes Igni look like an internal research log rather than a language. Do this before v0.16 ships anything new.

**2 — Resolve the `bind:` asymmetry as an explicit, named limitation in the Property Applicability appendix.** Add a row: "`bind: shared.X` — supported on `toggle/checkbox/slider/dropdown`; rejected on `input` (use local + `on change:` writeback)." The asymmetry isn't going away in v0.16 (the implementation reason is real), so make it a single visible rule in the reference table rather than something a reader has to reconstruct from prose. While there, add the each-loop rejection.

**3 — Pin the semantic uncertainties from Q3 in a "Runtime semantics" appendix.** You don't need to design new features; you need to write down the answers to questions like "is `is` reference or value equality?" and "what does an in-flight fetch do when its dependency changes?". An LLM cold-test session that asks these questions explicitly would surface the gaps quickly. This is the v0.16 spec change with the highest LLM-correctness payoff per word added. Particularly urgent: equality semantics, `each`-iteration support beyond lists, and fetch-cancellation behaviour.

**4 — Cut the multi-view-screens section or demote it to the cookbook.** It's a tactical workaround for missing navigation, presented at spec level with hedging prose. The spec budget rule applies: if the answer is "use a real navigation system" once one exists, the workaround shouldn't be canon. v0.17 or v0.18 should land basic navigation primitives (modal, replace, stack-clear) — once those exist the multi-view section becomes deletable.

**5 — Split CLAUDE.md.** Extract design principles + non-negotiables into PRINCIPLES.md (read by humans and AI alike, linked from README). Keep CLAUDE.md focused on the working contract: cycle, plan-mode, SYNC markers, append-only conventions, "honest no". This makes the principles citable in spec PRs without dragging in working-with-Tyr process material, and reduces the surface area of the doc that has to stay current.

**6 (v0.16 candidate) — `count` should accept a predicate, OR the spec should explain why it doesn't.** This is the smallest change that removes the sharpest cross-builtin inconsistency. `count(alerts, a => a.level is "critical")` is the obvious thing to write. If you've decided against it for a real reason (e.g., zero-arg builtin parse simplicity), state the reason. If not, ship it.

**7 (v0.17+) — Decide what `each` does over non-lists, and what the canonical "do this N times" idiom is.** Range iteration, string iteration, and per-item indexing are all common needs whose absence isn't documented. Adding a `range(n)` builtin is the smallest path; alternatively, add an optional `, index: i` clause to `each`. Either is a small spec addition with high practical leverage.

**8 (research direction) — Run a cold-LLM round specifically on the semantic uncertainties.** Build a prompt that asks the model to predict what 10 carefully-chosen ambiguous-by-spec snippets do, then check whether the spec or runtime matches. Convergent wrong answers are gold — they tell you exactly which prose isn't pinning behaviour. This is methodologically continuous with what you're already doing but targets a different defect class than "models invent syntax" — it targets "models guess semantics correctly." That's the next frontier for the dissertation contribution.

**Convergences worth naming explicitly.** I agree with: lexical reactivity as the single rule (don't add a `derived:` keyword); `shared.X` prefix (don't hide it); compile-time rejection of the fetch-input footgun (this is the right level); the budget-not-backlog framing; the token-only `max_width:` decision (don't add `full`); "no deep links yet" being honestly listed as deferred rather than papered over. These are the choices I would defend if asked to review a PR proposing to change them.

The project is in unusually good shape for a one-person dissertation prototype. The biggest risks are the three documents drifting in tone (spec for researchers, README for users, CLAUDE.md for AI) and the v0.15 patch-notes-at-the-top regression. Both are cheap to fix.

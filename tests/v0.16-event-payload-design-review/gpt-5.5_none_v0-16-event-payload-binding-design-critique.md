1. **Q1 — Shape choice.** I converge with the default: **Shape A is the right design**. `on X(name):` is explicit, local, low-syntax, and matches the existing mental model of “this block has a parameter,” without introducing a second handler style. The parens are not a serious ambiguity in Igni because they appear after an event name in `on`-handler position, not after a component name, and component invocation still remains paren-free: `Stepper value, on increment(amount): ...` reads structurally differently from `greet(name)`. The main counter-argument is visual: readers from JS/Flutter may initially parse `increment(amount)` as “call increment,” but the trailing colon and `on` keyword should quickly disambiguate it. Shape B’s implicit `value` is worse because it violates “no magic.” Shape C makes handlers expression-like when Igni handlers are statement bodies. Shape D adds a new token for no real gain. Possible Shape E forms like `on submit as text:` or `on submit text:` are not better: they either add a keyword or create a looser, less visually bounded binding. Shape A is the cleanest fit.

2. **Q2 — Mismatch cases.** I mostly converge with the proposed asymmetry: **payload emitted + bare handler should silently drop; payload-less emit + named handler should be a static error**. Ignoring an event payload is a legitimate use case, and forcing a dummy name would add noise and invite conventions like `_` that Igni does not otherwise need. `on submit:` should mean “run this when submit happens; I do not care about the value.” The reverse case is different: `on close(reason):` visibly claims a value exists, so accepting it would create exactly the kind of hidden runtime `null`/undefined behavior Igni should avoid. One wording correction: for custom component events this is not really a parse-time error unless the parser already knows the component’s event signature; it is a compile-time/static validation error. Reserved events can be rejected at parse time, but payloadless custom emits require cross-component checking.

3. **Q3 — Multi-value emit.** I converge with the default: **keep single positional payload plus object packing**. Multi-arg events would add arity rules, ordering hazards, handler arity mismatch cases, and parsing complexity around commas for very little gain. Object packing is more Igni-shaped: the payload is one visible thing, field names carry meaning, and the event can evolve without positional churn. `emit submit {email: e, name: n}` plus `on submit(data): handle(data.email, data.name)` is more self-documenting than `emit submit e, n` plus `on submit(email, name): ...`, especially for LLM generation. Keeping one payload also aligns with “one way to do everything”: if you need multiple values, make the one value an object.

4. **Q4 — Reserved events.** I converge with the rule that **reserved events stay payload-less for v0.16**, including rejecting `button "X", on tap(coords): ...`. That keeps the primitive event surface simple and avoids platform-specific questions like pointer coordinates, touch phases, keyboard modifiers, changed value semantics, etc. `change` is the awkward one, because many UI frameworks make “change” carry the new value, but Igni already has `bind:` for value flow, and preserving that separation is cleaner: primitive `change` is a notification; value synchronization is explicit binding. However, the design note should patch one inconsistency: the earlier example `Slider on change(v): volume = v` conflicts with “reserved `change` is payload-less” if `change` is globally reserved. Either remove that example or rename the custom event to a non-reserved domain event such as `changed`, `selected`, or `set`. I would keep reserved names globally reserved rather than context-overloaded.

5. **Q5 — Pattern preservation.** Shape A does not appear to break the closure-over-loop-variable pattern; `each alert in alerts: AlertRow alert, on delete: ...` still works because the handler binds no payload and closes over `alert` normally. The mixed case also works if scoping is specified clearly: in `on delete(deleted_id): ...`, both the loop variable and handler parameter are in scope, and the handler parameter should shadow any same-named outer variable. The main existing-pattern risks are not Shape A itself but the static validation it enables. First, components must not emit the same event sometimes with a value and sometimes without; that should become a compile-time error because otherwise `on X(name):` cannot be checked cleanly. Second, if any existing examples or user code use reserved `change` as a custom payload event, Q4’s rule would break or reject them. Third, the spec should explicitly show multi-line handler bodies with parameters so readers know `on submit(data):` works both inline and with an indented block. Overall, Shape A preserves existing idioms, but the event-signature consistency rule needs to be made explicit.

**Q1 — Shape choice.** Shape A is right, and I converge with the default. The mis-cue risk is real but overstated: the `on` keyword is a hard syntactic anchor — there is nothing else in Igni where `identifier(name):` follows `on `, so once a reader has parsed `on submit`, the parens have only one possible meaning. The component-invocation collision the design note worries about (`Stepper value, on increment(amount):`) is actually clearer than function-call collision because component invocations have *no* parens at the call site, so any parens inside a component-invocation argument list are unambiguously not invocation syntax. Shape B is correctly rejected — implicit `value` is exactly the kind of action-at-a-distance Igni's no-magic principle exists to forbid, and it would be the single biggest LLM-accuracy regression in the language (an LLM seeing `value` in scope has no source-visible way to know where it came from). Shape C conflates expression-lambdas with statement-bodies and would force a second handler form. Shape D's `->` is a new symbol with no other use in the language — pure spec-budget tax. The one Shape E worth naming-and-rejecting is `on submit as query:` — it reads naturally in English and avoids the parens-look-like-a-call concern, but `as` isn't used anywhere else in Igni either, so it's a new keyword for zero gain over parens, which already match the lambda-parameter convention (`item => item.foo`). Shape A wins because parens-around-binding-name is already the established Igni shape for "this identifier is the parameter of the thing to its left."

**Q2 — Mismatch cases.** The asymmetry is correct but the **silent drop** half is wrong, or at least under-specified. Parse-time error on `on X(x):` when the child's `emit X` is payloadless is clearly right — it's statically detectable, the error message is obvious, and it catches a real bug class (parent expecting data the child never sends). But silent-drop in the other direction violates the no-magic principle just as much as Shape B did: a child emits a value, the value vanishes, and nothing in the source explains where it went. I'd argue for **parse-time warning, not error, not silent**: the parent's bare `on X:` should be legal (because forcing parents to bind values they don't need would be ceremony tax, especially for fire-and-forget events), but the transpiler should surface "child emits payload, handler does not bind it" as a diagnostic. If warnings aren't in Igni's tooling vocabulary yet, then make it a parse-time *error* and require parents to write `on X(_):` to explicitly discard — this matches the "every alternative is a branch where an LLM can guess wrong" principle by removing the silent path entirely. Silent drop is the worst of three options because it's invisible.

**Q3 — Multi-value emit.** Keep the single-positional + object-packing rule. I converge with the default, strongly. Multi-arg emit creates exactly the parsing ambiguity the design note flags (`Stepper value, on increment(a, b):` — is `b` a second handler parameter or a second component prop? the comma is overloaded), and it creates a second way to express multi-value payloads when object-packing already works. Object-packing also has the underrated property of being **self-documenting at the emit site**: `emit submit {email: e, name: n}` tells you at a glance what the payload shape is, whereas `emit submit e, n` requires the reader to find the component definition to know what those positions mean. For an LLM reading partial code, named-object-packing is dramatically more recoverable than positional. The only case where multi-arg would feel natural is two-value emits like `emit moved x, y` — but even there, `emit moved {x, y}` (with shorthand object syntax, if Igni has it) is barely longer and reads better.

**Q4 — Reserved events.** Keep them payload-less for v0.16, but the rationale in the design note is slightly weak and worth firming up. The real reason isn't "they happen to be payload-less today" — it's that `tap`, `change`, and `touch` are **primitive bindings to platform events**, not user-defined emits, so allowing `on tap(coords):` would require the language to specify what the payload IS (click coordinates? relative or absolute? in what unit?), which is a much bigger spec commitment than just "custom events can carry a value the user defined." That spec commitment is exactly the kind of thing v0.16 should not be making in a syntax-shape note. So: reject `on tap(coords):` at parse time with a message like "reserved event `tap` is payload-less; use `bind:` for value channels or define a custom event". The `change` case the note flags as "interesting" should stay handled by `bind:` — having two ways to read a changed value (bind vs on change(v)) would be a textbook one-way-to-do-everything violation. If a future version wants tap-with-coordinates, that's a separate event name (`emit tapped {x, y}` on a custom component, or a new reserved event like `tap_at`) — don't overload the existing primitive.

**Q5 — Pattern preservation.** The closure-over-loop-var case is preserved cleanly, and the shadowing rule for the mixed case (named handler parameter shadows outer loop variable) is the right call — it matches how every other lexically-scoped language handles this and an LLM will guess it correctly zero-shot. Two patterns worth surfacing that the note doesn't: **(a) Handler bodies that reference parent-scope state with names that might collide with conventional payload names.** If a parent has a `query` variable in scope and writes `SearchBar on submit(query): results = fetch(query)`, the handler's `query` shadows the outer one — fine, but worth a cheatsheet note because the bug ("why isn't my outer `query` updating?") is subtle. **(b) Nested components emitting up through intermediates.** If `Form` contains `SearchBar` and wants to re-emit upward, you'd write `SearchBar on submit(text): emit search text` inside Form's body — this works under Shape A but it's worth a worked example because it's the canonical "lifting state up" pattern and currently has no spec coverage. Neither is a *break*; both are gaps the cheatsheet update should fill while it's open. Beyond those, I don't see Shape A breaking anything — the design is genuinely additive over the current bare-`on X:` form.

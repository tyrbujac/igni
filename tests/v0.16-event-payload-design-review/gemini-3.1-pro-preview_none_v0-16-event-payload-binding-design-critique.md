**Q1 — Shape choice.** I explicitly converge with **Shape A**. It aligns perfectly with Igni's "no magic" and "spec budget" principles by reusing the mental model of function definitions: parens declare bindings (`greet(name)` vs `on submit(text):`). Shape B (implicit `value`) is a severe violation of "no magic" that would frequently cause LLM hallucinations. Shape C (lambdas) violates "one way to do everything" by introducing a second handler body style for statement blocks. Shape D (`->`) taxes the spec budget with a new symbol. A hypothetical Shape E without parens (`on submit text:`) would risk visual ambiguity with component invocations (which explicitly omit parens for arguments). Because the `on` keyword precedes the event name and a colon terminates the declaration, the parens in Shape A are structurally unambiguous and highly unlikely to be mis-cued as a function call by either humans or LLMs.

**Q2 — Mismatch cases.** I strongly agree with the proposed asymmetry: silent drop for unused emitted values, and parse-time error for requesting non-existent payloads. This perfectly mirrors standard lexical safety. Discarding an emitted value is a structurally safe operation (the parent simply doesn't care about the payload, common in UI where an event might just trigger a refresh), whereas requesting a named payload from an event that emits nothing is inherently unsafe and indicates a developer or LLM hallucination. Catching the latter at parse time leverages Igni's cross-component static checking, cleanly satisfying the "no magic" directive by refusing to populate uninitialized bindings.

**Q3 — Multi-value emit.** I converge with keeping the existing single-positional + object-packing rule. Adding a multi-arg event signature would directly violate "one way to do everything" by forcing developers (and LLMs) to choose between comma-separated args and object-packing. Object-packing is already an established Igni idiom, it naturally scales to highly complex payloads (like forms), and it avoids taxing the parser with new comma-delimited boundary rules between event names, parameters, and trailing colons. Optimizing for rule simplicity over output verbosity dictates that we stick to the single-value constraint.

**Q4 — Reserved events.** The default proposal to keep reserved events (`tap`, `change`, `touch`) payload-less is the correct path. For primitive state manipulation (like `change`), Igni already utilizes the `bind:` syntax to synchronize state; allowing `on change(v):` would introduce a second, competing way to observe built-in primitive updates, violating the "one way to do everything" mandate. By restricting named payloads strictly to custom `emit` boundaries, you keep the spec rules mutually exclusive and cleanly separate primitive state synchronization from custom event messaging. 

**Q5 — Pattern preservation.** Shape A successfully preserves existing patterns without introducing structural breakage. The closure-over-loop-variable pattern remains intact because Igni already relies on standard lexical scoping, and the design note's shadowing rule (payload parameter shadows outer loop variable) is standard, predictable behavior. The syntax also composes safely with component properties (e.g., `Stepper value, on increment(amount): count = count + amount`); the comma clearly separates the component's positional argument from the event handler, and the parens safely encapsulate the payload identifier away from the component invocation space. There are no dangling ambiguities here.

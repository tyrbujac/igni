**Q1 — Each / every parallel.** The parallel is real but weaker than the note claims, and the weakness is exactly where you point: `each`'s body in current Igni is render-only (it produces UI), while `every`'s body is reassignment-only (it produces state changes). They share "language-driven iteration" at the *trigger* level but diverge at the *effect* level — one builds a tree, the other mutates state. That's not a fatal asymmetry, but it does mean a model reasoning "every is each-for-time" will get the trigger right and the effect wrong. On (b), I don't think the `each` parallel teaches lifecycle at all — `each` has no lifecycle, it's a pure expansion at render time. A model would have to learn `every`'s mounted-pause-resume rule from the spec text directly; the parallel gives it nothing. On (c), the lexical near-rhyme is a mild hazard for skim reading specifically because the bodies look so different — a reader skimming `every 1s:` and parsing it as `each ...` will be briefly confused when the body has no loop variable. I'd call it a wash overall: the semantic parallel is genuine enough to defend the keyword choice against "why not `tick`/`timer`/`interval`," but the note oversells it as a teaching aid. The real defence of `every` is the user-action invariant, not the each-parallel.

**Q2 — User-action invariant.** The invariant is real but thinner than the note treats it. On (a): `on change:` already has a soft edge — if a bound variable is reassigned programmatically (e.g. `count = 0` in a Reset button's `on tap:` body, where `count` is also bound to an input), does `on change:` fire? The spec doesn't say in the excerpt I'm given, but in either answer the invariant erodes: if it fires, `on change:` is already not strictly user-driven; if it doesn't, the rule is "user-driven OR programmatic, depending on path," which is exactly the kind of implicit class boundary the note is trying to protect. So the invariant is more aspiration than load-bearing fact. On (b), `on websocket-message:` and `on geolocation-update:` are the more interesting test — these are external-but-not-user-driven, and they sit awkwardly in either family. If they go in `on X:`, the invariant is already dead and `on tick:` was fine. If they get their own keywords (`when message:`, `every location:`?), then `every` is consistent with that future. I think the note is right that *external system events* deserve syntactic separation from *user events*, but it should defend that as the principle ("on X: is for user input; everything else gets its own shape") rather than the narrower "user-action invariant," which is fragile under scrutiny. On (c): even granting the invariant is shaky, the variable-rate argument carries the decision on its own. `on tick:` foreclosing the duration argument is the harder cost; the invariant is a nice-to-have justification stacked on top. So Shape A is right, but the note over-leans on the weaker of its two arguments.

**Q3 — Duration whitelist.** Shipping only `1s` is artificially restrictive and I'd push back here. The token-first commitment makes sense for `max_width:` because the four breakpoint tokens cover the design space — there's no obvious "missing" value. For durations, `1s` covers exactly one of the friction surfaces the note itself enumerates: countdowns and clocks. Animations want `100ms` or faster; auto-save wants `5s`; auto-refresh wants `30s`. The note lists all of these as motivating cases and then ships a whitelist that excludes all of them. On (b), yes, this will hurt — a model that reaches for `every 100ms:` for an animation hits a parse error and the error message ("v0.14 supports `1s` only") doesn't tell it what to do instead. The honest answer ("animations aren't supported yet") is missing from the error and from the spec. The model will either misattribute (think it got the syntax wrong and try `every 100 ms:`, `every 0.1s:`, etc., burning turns) or correctly conclude "Igni can't do this app" — neither outcome is what you want. On (c), I'd ship `1s`, `100ms`, `5s`, and `30s` together. All four have named real-app friction surfaces in the note, all four lex identically, the parser cost is one whitelist set instead of one whitelist value, and you avoid four future design-note rounds for what is structurally one decision. The "real apps drive promotion" thesis works when each promotion is a genuine new shape; here the shape is fixed and only the whitelist entry changes. Bundling is the cleaner call.

**Q4 — One `every` per screen.** This is where I'd push hardest. Auto-save at 5s + auto-refresh at 30s is a genuine real-app composition — a notes app, a draft editor, a dashboard. The workaround ("compose via shared timestamps inside one `every 1s:`") only works if `1s` is fast enough for the highest-rate need *and* the user is willing to write modular-arithmetic gating logic inside one block. That logic is exactly the kind of footgun the language is supposed to eliminate: the developer writes `if tick_count % 5 == 0:` and `if tick_count % 30 == 0:` and now has to maintain a counter, reset it sensibly, and reason about phase. Models will write this wrong. On (b), yes — a model with two recurrences will absolutely write two `every` blocks; that's the natural shape. Parse-time rejection will feel arbitrary, and the error message has no good remediation ("merge them into one block and use modular arithmetic" is not Igni-flavoured advice). On (c), the composability claim doesn't hold once you add the `100ms` whitelist entry — you can't compose `100ms` and `5s` recurrences in a single block at all without sub-stepping, and sub-stepping inside an `every 100ms:` body to get a `5s` event is exactly the kind of manual driver the note is trying to eliminate. I'd lift the restriction: allow multiple `every` blocks per screen, each with its own duration token. The implementation cost is trivial (a list of `Timer.periodic` instances instead of one), and the simplicity argument doesn't survive the second real-app case.

**Q5 — Mounted-only lifecycle.** Mounted-only is the right *default* but wrong as the *only* option. (a) Session timers are the canonical counterexample — "your session expires in 30 minutes" must survive navigation, and the v0.15+ punt to app-scope `every` leaves a gap during which apps either can't express this or work around it with something hacky. (b) The Settings sub-screen polling case is more ambiguous — most polling probably *should* pause when the user navigates away, and the navigate-back-resumes rule is what most apps want. But "polling that should survive a sub-screen excursion" is a real case for things like a dashboard with a detail drawer. (c) User-visible glitches: a clock display that pauses for 8 seconds while the user is in a sub-screen and then resumes mid-second will look fine because clocks resync from `format_time()`, but a countdown that pauses-and-resumes will display wrong unless it's reading from a wall-clock timestamp rather than decrementing. The Pomodonut example in the note decrements `remaining` — which means navigating away from the timer screen *pauses the pomodoro*, which is almost certainly not what the user wants. That's a silent semantic bug introduced by the lifecycle rule, and it shows up in the very example the note ships. I don't think app-scope `every` belongs in v0.14 — that's genuine scope creep and deserves its own design — but the Pomodonut example should either use a wall-clock-timestamp pattern (capture `start_time`, compute `remaining` from `clock() - start_time`) or the note should acknowledge that the screen-scope lifecycle pauses the timer on navigate-away and that this is a known limitation pending app-scope `every`. Right now the example silently relies on the user not navigating, which is the kind of magic the language is supposed to forbid.

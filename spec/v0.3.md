# Rocket Language Spec v0.3

**By Tyr | 11/04/26 | Status: Design Stage**

Rocket is a UI-first programming language designed for human readability and LLM accuracy. Its north star is "Flutter, without the bracket hell" — the same cross-platform power (web, mobile, desktop) but with code that reads like a design spec.

It prioritises: readability, simplicity, and minimal ambiguity.

**Changes from v0.2:** Async data with loading/error as a first-class concept (`is loading`, `is error`). Mutation requests via `method:` and `body:`. `on tap:` attaches to any primitive, layout, or component, not just `button`. Pagination via `each ..., paginate: N:`. Functions defined inside a screen close over its state. The lexical reactivity rule is now stated explicitly. Option A (no parentheses on component invocation) is committed, with the rule that components are never passed as arguments to other components. Two new design principles: *setup is part of the language* and *the spec is a budget, not a backlog*. Optimistic updates deferred to v0.4.

---

## Design Principles

- Indentation-based scoping (no braces, no brackets for blocks)
- Colons end any line that opens a block
- One way to do everything — no aliases, no shortcuts, no alternatives
- Types are inferred, with optional hints where ambiguous
- Max nesting depth: 4 levels per component (custom components reset the counter)
- Everything a component needs lives in one file
- Zero magic — if something happens, you can see it in the code
- **Setup is part of the language.** Three commands to first pixel:
  ```
  install rocket
  rocket new my-app
  rocket run
  ```
  Browser opens. No SDK installer, no Android Studio, no Xcode, no `flutter doctor`, no Gradle, no `pubspec.yaml`. Web is the v1 target precisely because it lets us hit this bar; mobile compilation is opt-in later.
- **The spec is a budget, not a backlog.** Every new keyword or block type is a tax on zero-shot LLM learnability. Features that compose from existing primitives are cheap; features that introduce new shapes are expensive. Prefer extending existing shapes.

## Variables

```
name = "Tyr"
count = 0
active = true
user: User = fetch("/api/user")
items: [Product] = []
```

No `var`, `let`, `const`, or `final`. Just `=`. One way.

---

## Functions

```
greet(name):
  return "hello " + name

validate(email):
  if email is empty:
    return false
  return true
```

Parentheses around arguments. Colon opens the block. No `def`, `func`, or `fn` keyword — the name followed by parentheses is enough.

Functions defined **inside a `screen` or `component`** close over the surrounding state and can read or write any variable declared there. Top-level functions cannot. This is how event handlers mutate screen state without prop-drilling:

```
screen Counter:
  count = 0

  layout vertical, gap: medium, align: center:
    label count, style: heading
    button "Add", on tap: bump()

  bump():
    count = count + 1
```

---

## Boolean Logic

Use `not`, `and`, `or` — not symbols.

```
active = not active
if logged_in and verified:
  show Dashboard
```

---

## Components

A reusable UI piece. No imports, no exports, no boilerplate. If it exists in the project, it can be used anywhere.

```
component Avatar(url, size):
  image url, size: size, round: true

component Stat(label, value):
  layout vertical, align: center:
    label value, style: heading.small
    label label, style: caption, color: subtle
```

Invocation has no parentheses — the component name followed by its arguments is enough:

```
Avatar user.avatar, size: 80
Stat "Followers", user.followers
```

**Components take data via arguments and contain other components via indentation. A component is never passed as an argument to another component.** This rule is what keeps invocation unambiguous without parentheses. If you want one component to render another, lift it into the outer component's body or pass the data and let the outer component build it.

**Arguments to components and screens are immutable.** To edit a value passed in, declare a local variable inside the body:

```
screen PostDetail(post):
  draft = post.title

  layout vertical, gap: medium, padding: large:
    input bind: draft, placeholder: "Title"
```

## Screens

A full page that can be navigated to.

```
screen Profile(user):
  layout vertical, align: center, padding: large:
    Avatar user.avatar, size: 80
    label user.name, style: heading
    label user.bio, style: body, color: subtle

    layout horizontal, gap: large:
      Stat "Followers", user.followers
      Stat "Following", user.following
      Stat "Posts", user.posts
```

---

## Layout

Two types: `vertical` and `horizontal`. Everything is arranged using layouts.

```
layout vertical, gap: medium, padding: large:
  label "Title", style: heading
  label "Subtitle", style: body
```

Properties: `gap`, `padding`, `align` (start, center, end), `spread` (space-between), `background`, `rounded`.

## Built-in Primitives

These are the core building blocks. All lowercase, always available.

| Primitive   | Purpose              | Example                                        |
|-------------|----------------------|------------------------------------------------|
| `label`     | Display text         | `label "Hello", style: heading`                |
| `image`     | Display an image     | `image user.avatar, size: 48, round: true`     |
| `button`    | Tappable action      | `button "Save", color: brand, on tap: save()`  |
| `input`     | Text entry           | `input bind: email, placeholder: "Email"`      |
| `toggle`    | On/off switch        | `toggle bind: dark_mode`                       |
| `checkbox`  | Tick box             | `checkbox bind: agreed, label: "I agree"`      |
| `slider`    | Range selector       | `slider bind: volume, min: 0, max: 100`        |
| `dropdown`  | Pick from options    | `dropdown bind: country, options: countries`   |
| `badge`     | Status indicator     | `badge "Online", color: green`                 |
| `spinner`   | Loading indicator    | `spinner`                                      |
| `divider`   | Visual separator     | `divider`                                      |

## Data Binding

Use `bind` to connect a primitive to a variable. Changes flow both ways automatically.

```
screen Settings:
  email = "tyr@example.com"
  dark_mode = false

  layout vertical, gap: medium, padding: large:
    input bind: email, placeholder: "Email"
    toggle bind: dark_mode
```

No `onChange`, no `setState`, no event payloads. `bind` is the only pattern for two-way data.

## Styling

No raw pixel values. Use design tokens from a theme.

```
theme:
  spacing:
    small: 8
    medium: 16
    large: 24
  text:
    heading: size 24, weight bold
    body: size 16
    caption: size 12, color: subtle
  color:
    brand: "#6C5CE7"
    subtle: "#999"
    danger: "#E74C3C"
```

Reference tokens inline: `style: heading`, `color: brand`, `padding: medium`.

---

## State

Variables are reactive. Change them and the UI updates automatically.

```
screen Counter:
  count = 0

  layout vertical, align: center, gap: medium:
    label count, style: heading
    button "Add", on tap: count = count + 1
```

**The reactivity rule:** *each screen re-evaluates from the top whenever any variable it lexically references is reassigned.* That's the entire model. If a variable's name appears in your screen body and you change its value, the screen re-renders.

No useState, no setState, no notifyListeners, no StreamBuilder, no reactivity primitives to learn.

## Async Data

Fetch data from a server with `fetch`. The assignment looks synchronous, but the screen knows the value arrives asynchronously and tracks three states for it: **loading**, **error**, and **loaded**.

```
screen Profile(user_id):
  user: User = fetch("/api/users/" + user_id)

  if user is loading:
    spinner
  else if user is error:
    label "Couldn't load profile", color: danger
  else:
    layout vertical, gap: medium, padding: large, align: center:
      Avatar user.avatar, size: 80
      label user.name, style: heading
      label user.bio, style: body, color: subtle
```

The rule: **a line that calls `fetch` (or any function returning async data) blocks until it resolves.** The variable starts in `loading`, transitions to either `error` or the resolved value, and the screen re-renders at each transition. `is loading` and `is error` are the only new tests — for the success case, just use the variable normally.

If multiple async assignments appear in the same screen, they fetch in parallel, and the screen is in `loading` until all of them have resolved (or any of them errors).

### Mutations

For requests that change server state, pass `method:` and `body:`:

```
screen PostDetail(post):
  draft = post.title

  layout vertical, gap: medium, padding: large:
    input bind: draft, placeholder: "Title"
    button "Save", on tap: save_post()

  save_post():
    result = fetch("/api/posts/" + post.id, method: "PATCH", body: {title: draft})
    if result is error:
      label "Couldn't save", color: danger
    else:
      navigate back
```

`method:` accepts `"GET"` (default), `"POST"`, `"PUT"`, `"PATCH"`, or `"DELETE"`. The result of a mutation has the same loading/error/loaded states as a read. Branch on `is error` for failure; continue normally for success.

That's the entire async model: one primitive (`fetch`), two new tests (`is loading`, `is error`), one new keyword (`is`). Everything else falls out of the existing state and reactivity rules.

## Conditionals

```
if user.online:
  badge "Online", color: green
else if user.away:
  badge "Away", color: gray
else:
  badge "Offline", color: gray
```

`else if` chains as many conditions as you need. No ternary operators. No inline conditionals. Only `if` / `else if` / `else`.

---

## Lists

```
each item in user.posts:
  PostCard item
```

For long lists fetched from a server, add `paginate:` to fetch in chunks and auto-load more on scroll:

```
each post in posts, paginate: 20:
  PostCard post
```

If the iterated variable is still loading (see *Async Data*), the `each` block renders nothing and the screen falls back to its loading state.

No `.map()`, no `ListView.builder()`, no keys, no index boilerplate.

---

## Events

```
on tap: save()
on tap: count = count + 1
on change: validate(email)
```

`on tap:` can attach to **any primitive, layout, or component invocation** — not just `button`. List items, cards, avatars, and whole layouts are all tappable the same way:

```
PostCard post, on tap: navigate to PostDetail post

layout vertical, on tap: expand():
  label item.title
  label item.subtitle
```

## Open Design Questions (v0.4)

Items that surfaced during v0.3 but haven't been worked out yet.

### Optimistic Updates with Rollback

The pattern "mutate the UI immediately, send the request in the background, revert on failure" is core to good apps. v0.3 supports the simpler pattern (spinner → wait → navigate on success). True optimistic updates require three orthogonal pieces:

- A way for a screen to mutate values it received as arguments, or a "shared store" concept that screens read and write.
- Background requests that don't block the screen's loading state.
- A way to surface a failure after the user has navigated away from the screen that triggered the request.

Each of these is its own design discussion. Deferred to v0.4.

### Other Areas for v0.4+

- Animations and transitions
- Forms and validation (multi-field, cross-field, async validators)
- Lists with search, filter, and sort
- Routing patterns: deep links, query params, modal stacks, back-stack management
- Mobile-specific patterns (gestures, bottom sheets, system back button)
- Theming and dark mode propagation
- Package/module system for sharing components across projects

## Test Prompts

### Easy case (smoke test)

> "Using only the Rocket language spec below, write a Settings screen with: a profile picture, username, email field, dark mode toggle, notification toggle, and a red logout button at the bottom."

If the LLM writes valid Rocket on the first try, the basics work.

### Hard case (the one that actually validates the language)

> "Using only the Rocket language spec below, write a screen that fetches a paginated list of a user's posts with loading and error states, navigates to a detail screen on tap, and lets the user edit and save the post title with feedback on success or failure."

If the LLM produces compilable Rocket on the first try with no invented syntax, the spec is learnable zero-shot. If it invents, those areas are still under-specified — and they're the ones that matter, because they're where Flutter LLMs fail today.

### Comparison test

Write a music player screen in both Flutter/Dart and Rocket. Show album art, song title, artist, a progress slider, and play/pause/skip buttons in a row. Compare line count, readability, and how many syntax errors appear in each version.
